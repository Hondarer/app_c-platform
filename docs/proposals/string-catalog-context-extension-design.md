# app 固有の文脈引数の設計

> [!NOTE]
> 本書は、トレース種別の文字列カタログへ、利用 app が定める文脈引数を追加できるようにするための提案文書です。
> トレース種別の設計については、[トレース種別の文字列カタログの設計](string-catalog-trace-kind-design.md) を参照してください。
> カタログを外部へ公開する場合については、[ライブラリのカタログを外部へ公開する設計](string-catalog-export-design.md) を参照してください。
> 同書は、本書が導入する文脈定義ファイルを app 単位のカタログ設定ファイルへ一般化し、参照名を `context` から `settings` へ改める統合案を示します。
> 現行仕様については、[文字列カタログの機能仕様](../functional-spec/string_catalog.md) を参照してください。

## 目的

本設計は、トレース種別のカタログ項目が受け取る文脈引数へ、利用 app が定める値を追加できるようにします。  
追加した値は、書式の位置指定から参照でき、条件式フィルターの判定対象になります。

生成器は 1 つのスクリプトのまま維持します。  
app ごとに生成器を複製せず、文脈引数の内容だけをデータとして差し替えられる構成とします。

## 解決する課題

要求 ID、セッション ID、相関 ID のように、app が実行時に保持する値をトレースへ含める要求があります。  
現在これを行うには、各カタログ項目の引数として定義し、すべての呼び出し位置で値を渡す必要があります。

呼び出しごとに同じ値を記述するため、記述の漏れが発生します。  
漏れた項目では値が欠けるため、条件式フィルターで一貫して参照できません。

生成器が付け加える文脈引数は、定数 `CONTEXT_ARGUMENTS` としてスクリプトへ埋め込まれており、cplat が定める 6 個に固定されています。  
app ごとに内容を変えるために生成器を複製すると、共通部分の修正が片方だけに適用される不整合が生じます。

## 適用範囲

本設計の対象範囲は、拡張する文脈引数の番号の割り当て、定義の受け渡し方法、生成器の変更、利用 app が満たす契約、および既存の規範の解除範囲です。

次の事項は、本設計の対象外とします。

- cplat が定める 6 個の文脈引数の内容の変更 (現行の内容を維持するため)
- 文字列リソース種別への文脈引数の追加 (呼び出し位置を付与しない種別のため)
- 条件式フィルターの構文 (フィルターから見ると通常の引数と区別がないため)
- 文脈値を保持する仕組みの提供 (値の生存期間と有効範囲は利用 app の責務のため)

## 設計の方針

### 文脈引数の解決をデータの連結として扱う

現在の生成器は、文脈引数を次の 5 項目だけで記述しています。  
値の取得式は `macro_value` と `inline_value` のどちらかで、前者は呼び出し位置で確定する値、後者は実行時に取得する値です。

| 項目 | 内容 |
|---|---|
| `name` | 引数名。仮引数名および条件式が参照する名前になります。 |
| `kind` | 引数種別。`ARGUMENT_TYPES` が持つ名前です。 |
| `description` | 説明。Doxygen コメントと引数配列へ出力します。 |
| `macro_value` または `inline_value` | 値の取得式。 |
| 参照するヘッダー | 取得式が必要とする公開ヘッダー。現在は `TRACE_HEADERS` が一括で保持します。 |

生成器のロジックには、個々の文脈引数に固有の分岐がありません。  
文脈引数を使用する処理は、この 5 項目と基底の番号だけを参照しています。

そのため、定数 `CONTEXT_ARGUMENTS` を、cplat が定める引数列と app が定める引数列を連結して返す解決処理へ置き換えます。  
出力処理は、基底の番号と引数列の組を順に処理する形へ一般化します。  
生成器の複製は行いません。

### 拡張の番号を固定する

app が定める文脈引数の基底を 46 番に固定します。  
値は生成器の定数として保持し、カタログ定義にも文脈定義にも記載しません。

この固定により、cplat が定める文脈引数は 40 番から 6 個が上限になります。  
7 個目を追加すると、app が書式へ記載した `{46}` の意味が変わるためです。  
cplat 側の文脈引数を増やす場合は、`CPLAT_STRING_CATALOG_ARGUMENT_MAX` の拡張と拡張の基底の移動を伴う非互換の変更として扱います。

app が定める文脈引数の個数の上限は、46 番から 49 番までの 4 個です。

### 定義を app 単位の文脈定義ファイルで受け取る

文脈引数の定義を受け取る方法として、次の 3 つを比較しました。

| 案 | 受け取り方 | 評価 |
|---|---|---|
| A | カタログ定義へ直接記載する | app が複数のトレース カタログを持つ場合に、同じ記述が複製されます。 |
| B | app 単位の文脈定義ファイルを、生成器のコマンド ライン引数で渡す | 複製は発生しませんが、カタログごとに makefile 断片へ引数の記述が必要です。 |
| C | app 単位の文脈定義ファイルを、カタログ定義からの相対パスで参照する | 複製が発生せず、makefile 断片の変更も不要です。 |

案 C を採用します。  
app 内の複数のカタログが 1 つの文脈定義ファイルを共有でき、参照関係をカタログ定義から読み取れるためです。

文脈定義をカタログ定義から分離する理由は、既存の方針との整合です。  
カタログ定義へ記載するのは、著者、日付、版、および文字列の一覧であり、cplat が定める仕様や app 全体に関わる設定は持ち込みません。

### 値の取得方法を実行時の取得に限定する

app が定める文脈引数では、`inline_value` だけを許可し、`macro_value` を禁止します。

`macro_value` を許可すると、関数形式マクロが `_with_source` 関数へ渡す仮引数が増えます。  
仮引数の個数は app ごとに変わりますが、呼び出し側が記述するマクロの引数は変わらないため、呼び出し側からは差が見えません。  
しかし、生成物の関数シグネチャが app の設定に依存することになり、生成物を読んだときの理解が難しくなります。

呼び出し位置で確定する値は、cplat が定める 4 個ですでに網羅しています。  
app が追加する値は実行時の文脈であるため、`inline_value` で表現できます。

## 拡張する文脈引数の仕様

### 番号の割り当て

| 位置指定 | 用途 | 定める主体 | 個数 |
|---|---|---|---|
| `{0}` から `{39}` | カタログ項目の引数 | カタログ定義の作成者 | 40 個まで |
| `{40}` から `{45}` | 呼び出し位置と実行文脈 | cplat | 6 個 (固定) |
| `{46}` から `{49}` | app が定める文脈 | 利用 app | 4 個まで |

app が定める文脈引数は、文脈定義ファイルの記載順に 46 番から詰めて割り当てます。  
記載しない番号を空けることはできません。  
番号を固定したい場合は、記載順を変更しない運用とします。

### 文脈定義ファイル

形式は JSONC とし、カタログ定義と同じ解析処理を使用します。

```jsonc
// app が定める文脈引数の定義です。
// この app のトレース種別のカタログ定義が、context から参照します。
{
    "headers": ["svc/trace/svc_trace_context.h"],
    "arguments": [
        {
            "name": "request_id",
            "kind": "STRING",
            "description": "処理中の要求の ID。要求の外では空文字列です。",
            "inline_value": "svc_trace_context_request_id()"
        }
    ]
}
```

| 項目 | 必須 | 内容 |
|---|---|---|
| `headers` | 省略可 | 取得式が必要とするヘッダーの一覧。生成物の `#include` へ追加します。 |
| `arguments` | 必須 | 文脈引数の一覧。1 個以上 4 個以下です。 |
| `arguments[].name` | 必須 | 引数名。cplat が定める文脈引数およびカタログ項目の引数と重複できません。 |
| `arguments[].kind` | 必須 | 引数種別。`UNUSED` を除く既存の種別を指定します。 |
| `arguments[].description` | 必須 | 説明。Doxygen コメントと引数配列へ出力します。 |
| `arguments[].inline_value` | 必須 | 値を取得する C の式。型付きラッパーの内部で評価します。 |

### カタログ定義からの参照

トレース種別のカタログ定義へ、文脈定義ファイルへの参照を追加します。  
値はカタログ定義ファイルからの相対パスです。

```jsonc
{
    "kind": "trace",
    "context": "../trace_context.jsonc",
    "author": "Tetsuo Honda",
    "strings": [ ... ]
}
```

`context` は省略できます。  
省略した場合は、cplat が定める 6 個の文脈引数だけを持ち、現在と同じ生成物を出力します。

文字列リソース種別で `context` を指定した場合は、定義の誤りとして通知します。

## 生成器の変更

### 変更する箇所

| 箇所 | 現在の実装 | 変更後 |
|---|---|---|
| 文脈引数の定数 | `CONTEXT_ARGUMENTS` を直接参照する | 基底と引数列の組の並びを返す解決処理を参照する |
| 引数名の重複の検査 | cplat が定める名前と照合する | cplat と app の双方の名前と照合する |
| 位置指定の許可集合 | 利用者の引数と 40 番からの範囲 | 組の並びから範囲を合成する |
| 引数配列の要素数 | 40 番に 6 を加えた値 | 最後に使用する番号に 1 を加えた値 |
| ヘッダーの対応表 | 40 番からの一覧を出力する | 組ごとに一覧を出力する |
| 引数配列の初期化子 | 40 番からの要素を出力する | 組ごとに要素を出力する |
| 追加するヘッダー | `TRACE_HEADERS` を出力する | `TRACE_HEADERS` と文脈定義の `headers` を連結して出力する |

型付きラッパーの出力処理は変更しません。  
`macro_value` と `inline_value` による振り分けをすでに行っており、引数列の内容に依存しないためです。

`@MODULE@_write()` も変更しません。  
可変長引数をそのまま組み立て関数へ渡すため、文脈引数の個数に依存しません。

### 検査の追加

生成器は、文脈定義に対して次の検査を行います。

- `arguments` の個数が 1 個以上 4 個以下であること
- 引数種別が既知であり、`UNUSED` でないこと
- `inline_value` を持ち、`macro_value` を持たないこと
- 引数名が、cplat が定める文脈引数と重複しないこと
- 引数名が、参照元のカタログ項目の引数と重複しないこと

引数名の重複を誤りとする理由は、型付きラッパーの仮引数名が重複し、コンパイル エラーになるためです。  
生成器の段階で、定義ファイルの位置を示して通知します。

### 再生成の判定

`--if-newer` の比較対象へ、文脈定義ファイルを追加します。  
文脈定義を変更したときに、参照しているすべてのカタログの生成物が更新されるようにするためです。

生成器は、カタログ定義を読み込んでから再生成の要否を判定します。  
文脈定義の参照はカタログ定義の内容から決まるため、判定の順序は変更しません。

## 生成物の構成

### 生成するヘッダーの対応表

文脈引数の対応表は、cplat が定める分と app が定める分を続けて出力します。

```c
 *  本カタログはトレース種別です。
 *  引数の 0 番からはカタログ定義が定める引数で、40 番からは生成器が付け加える文脈引数です。
 *  {40} source_file_path : 呼び出し位置のソース ファイル。
 *  ...
 *  {45} thread_id        : 出力を要求したスレッドの ID。
 *  {46} request_id       : 処理中の要求の ID。要求の外では空文字列です。
```

### 生成するソースの引数配列

引数配列の初期化子は、基底ごとに指示付き初期化子で出力します。  
番号の間にある未使用のインデックスは、要素を明示しないことで値を受け取らない状態になります。

```c
static const cplat_string_catalog_argument s_arguments_0[] = {
    {CPLAT_STRING_CATALOG_ARGUMENT_KIND_UINT32, 0, "queue_length", "待ち行列の長さ。"},
    /* 1 番から 39 番は、要素を明示しないことで値を受け取らないインデックスになります。 */
    [40] = {CPLAT_STRING_CATALOG_ARGUMENT_KIND_STRING, 0, "source_file_path", "..."},
    ...
    [46] = {CPLAT_STRING_CATALOG_ARGUMENT_KIND_STRING, 0, "request_id", "..."},
};
```

app が定める文脈引数を使用する場合、配列の要素数は 47 要素から 50 要素になります。  
1 要素 24 バイトのため、1 項目あたり約 1.2 キロバイトの読み取り専用データになります。

### 型付きラッパー

`_with_source` 関数の内部で、`inline_value` の式を評価して渡します。  
呼び出し側が記述するマクロの引数は変わりません。

```c
static inline int sample_trace_key_state_dump_with_source(uint32_t queue_length, const char *source_file_path, ...)
{
    return sample_trace_write(SAMPLE_TRACE_KEY_STATE_DUMP, queue_length, source_file_path, ...,
                              cplat_process_get_pid(), cplat_process_get_tid(),
                              svc_trace_context_request_id());
}
```

## 利用 app が満たす契約

`inline_value` の式は、トレースの出力要求ごとに評価されます。  
利用 app は、次の条件を満たす取得処理を用意します。

- 軽量であること。出力の要求ごとに評価されるため、入出力や待ち合わせを含めないでください。
- 失敗しないこと。戻り値で誤りを通知する経路がないため、値を取得できない場合の既定値を自分で決めてください。
- スレッド セーフであること。出力を要求するスレッドから並行して評価されます。
- 値が未設定の場合の表現を決めること。要求の処理外など、文脈が存在しない場合に何を返すかを定めてください。

引数種別が `STRING` の場合、返すポインターは書式の組み立てが完了するまで有効である必要があります。  
スレッド ローカル記憶域の静的なバッファーを返す方式を想定しています。

`STRING` に `NULL` を返した場合は異常終了せず、`NULL` を示す既定の文字列へ展開します (`prod/libsrc/cplat/string_catalog/string_catalog_render.c` の `CPLAT_STRING_CATALOG_ARGUMENT_KIND_STRING` の分岐)。  
ただし、未設定を表すのであれば空文字列を返す方が、ログの解析が容易です。

## 既存の規範との関係

`app/string-catalog-sample/AGENTS.md` は、生成物が依存してよいものを、cplat の公開ヘッダーと標準ヘッダーだけと定めています。  
app が定める文脈引数を使用する場合、生成物はその app のヘッダーへ依存するため、この規則を解除する必要があります。

解除の範囲は、文脈定義ファイルを参照するカタログに限ります。  
依存先は文脈定義ファイルの `headers` に列挙され、1 か所に集約されます。  
生成物を別の場所へ持ち運ぶ場合は、文脈定義ファイルと取得処理を伴うことを条件とします。

この解除は、規範を設けている app に対して個別に行います。  
文脈定義を使用しない app の生成物は、従来どおり cplat の公開ヘッダーと標準ヘッダーだけに依存します。

## 互換性

文脈定義を参照しないカタログの生成物は、本設計の実装後も内容が変化しません。  
文字列リソース種別の生成物も変化しません。

`CPLAT_STRING_CATALOG_ARGUMENT_MAX` は 50 のまま変更しません。  
ライブラリ側の変更は発生せず、変更は生成器と文書に閉じます。

## 段階的実装計画

### 第 1 段階: 文脈引数の解決処理への置き換え

生成器の内部で、`CONTEXT_ARGUMENTS` の直接参照を、基底と引数列の組の並びを返す解決処理へ置き換えます。  
この段階では app が定める引数列を常に空とし、生成物が 1 バイトも変化しないことを既存の生成物との比較で確認します。

### 第 2 段階: 文脈定義ファイルの受け入れ

カタログ定義の `context` と文脈定義ファイルの読み込み、検査、および再生成の判定への反映を実装します。  
生成器の単体テストで、番号の割り当て、名前の重複の検出、個数の上限、および `macro_value` の拒否を確認します。

### 第 3 段階: サンプルによる確認

`app/string-catalog-sample` へ文脈定義ファイルと取得処理を追加し、書式から `{46}` を参照する項目で出力を確認します。  
1 つの文脈定義を複数のカタログ定義が参照する構成も、あわせて確認します。

## 検討事項

- **文脈定義ファイルの置き場所**:  
  app 内の複数のカタログが共有するため、カタログ定義と同じディレクトリに置くとは限りません。  
  相対パスで参照する方式は場所を制約しませんが、推奨する置き場所を規範として定めるかを決定する必要があります。
- **取得処理の初期化の責務**:  
  `inline_value` の式は、カタログの初期化とは無関係に評価されます。  
  取得処理が初期化を必要とする場合、初期化前の呼び出しで何を返すかは利用 app の責務になります。  
  この契約を機能仕様へ記載するか、文脈定義ファイルの注意事項に留めるかを決定する必要があります。
- **条件式フィルターからの参照**:  
  app が定める文脈引数は、フィルターからは通常の引数として見えます。  
  カタログをまたいで同じ名前を使う運用を前提にするか、名前の一貫性を利用 app の責務とするかを決定する必要があります。
- **引数配列の大きさ**:  
  app が定める文脈引数を使用すると、項目ごとの引数配列が最大 50 要素になります。  
  項目数が多いカタログでは読み取り専用データが増えるため、実測に基づいて許容範囲を判断する必要があります。
- **複数の文脈定義の合成**:  
  ライブラリとして提供される app と、それを利用する app が、それぞれ文脈引数を持つ構成は想定していません。  
  必要が生じた場合の合成方法は、本設計の対象外とします。
