# hashtable 可変長ストレージの管理方式

本書は、`cplat` の hashtable が可変長キーと可変長値のストレージをどのように管理しているかを説明します。

公開 API の一覧は [API チート シート](https://github.com/Hondarer/app_c-platform/blob/main/docs/api-cheatsheet.md)、契約の正本は公開ヘッダー `prod/include/cplat/hashtable/hashtable.h` です。  
実装は `prod/libsrc/cplat/hashtable/hashtable.c` です。

## 全体像

可変長キーと可変長値は、それぞれ専用のストレージ領域へ NUL 終端文字列として詰めます。

各レコードは 16 バイトの descriptor を持ち、ストレージ内の位置と長さを指します。

```c
struct hashtable_string_ref
{
    uint64_t offset;
    uint64_t length;
};
```

`length` が 0 のときは未使用です。

ストレージの空き領域は、descriptor とは別に「空きリスト」で管理します。  
確保はこのディレクトリの先着適合で行い、既存ブロックを動かしません。

通常の `cplat_hashtable_create` では、ストレージ容量は構築時に固定し、自動拡張しません。  
連続領域が不足した場合は `CPLAT_ERR_STORAGE_FULL` です。

## 空きリスト

空きリストは、オフセットの昇順に並べた空きブロックの配列です。

文献でいう address-ordered free list にあたります。  
確保の探索は first fit (先着適合)、解放時に隣接する空きブロックをまとめる操作は coalescing に対応します。

連結リストではなく密な配列で持ちます。  
要素数の上限が `capacity + 1` と決まっており、ポインターを持たない配置にできるためです。

### 不変条件

- 要素は `{uint64 offset, uint64 length}` で、`hashtable_string_ref` と同じ 16 バイトです。
- オフセットの昇順に厳密に並びます。
- 隣接する空きブロックは必ず結合します。すなわち、前の空きブロックの終端は次の空きブロックの開始より真に小さい値です。
- 空きブロックと使用中ブロックは `[0, storage_size)` を過不足なく分割します。
- 長さが 0 の要素は持ちません。
- 構築直後と `cplat_hashtable_clear` の直後は、要素数 1 で内容は `{0, storage_size}` です。

### 要素数の上限

空きブロックは使用中ブロックで区切られるため、使用中ブロックが L 個なら空きブロックは最大で L + 1 個です。  
L の上限は `capacity` のため、要素数の上限は `capacity + 1` です。

領域はこの上限ぶんを常に確保します。  
空きブロックの途中を確保して空きブロックが 2 個へ分かれる場合も、同時に使用中ブロックが 1 個増えるため、上限を超えません。

### 領域レイアウト

空きリストは、それぞれのストレージの直前に置きます。  
ストレージ自体は、従来どおり各領域の末尾のままです。

```
管理領域 (可変長キーのとき):
    | magic + version         |
    | header                  |
    | bucket_head[N]          |
    | entries[N]              |
    | key free list           |  // {offset, length} x (N + 1)
    | key storage             |  // key_storage_size バイト

データ領域 (可変長値のとき):
    | value refs[N]           |
    | value free list         |  // {offset, length} x (N + 1)
    | value storage           |  // value_storage_size バイト
```

要素数は永続化ヘッダーの `key_free_count` と `value_free_count` が持ちます。  
いずれも永続化して意味のある状態であり、実行時のみ有効なアドレスや一時フラグではありません。

## 操作と計算量

### 自動拡張

`cplat_hashtable_create_growable` で構築したテーブルは、通常の追加または更新で領域が不足すると、新しい内部領域へレコードを移してから要求された操作を再実行します。  
新しい容量は現在値の 2 倍を基本とし、操作を完了するための必要量が大きい場合は必要量を採用します。  
更新では新しいブロックを確保してから古いブロックを解放するため、必要量には一時的に共存する新旧ブロックを含めます。

総空き容量が足りていて連続領域だけが不足する場合は、容量を増やさず同容量の領域へ詰め直します。  
移行先で要求操作まで成功してから元のハンドルを切り替えるため、確保、移行、または要求操作が失敗した場合は元の領域と内容を維持します。

自動再構築は全レコードを移すため O(N + U) です。  
N はレコード数、U は使用中ストレージのバイト数です。

H を空きブロックの個数とします。

| 操作 | 実装 | 計算量 |
| --- | --- | --- |
| 確保 | 先頭から先着適合で走査し、空きブロックを縮小または分割する | O(H) |
| 解放 | 挿入位置を求め、前後の空きブロックと結合する | O(H) |
| 圧縮 | 空きブロックを辿って使用中区間を左詰めし、descriptor を更新する | O(N log H + U) |

N は `capacity`、U は使用バイト数です。

断片化していないとき H は 1 です。  
このため、確保と解放は実質 O(1) で完了します。

`capacity` 件の充填は O(N)、`cplat_hashtable_resize` と `cplat_hashtable_rebuild_into` も O(N) です。

### 確保の探索順

確保は、空きブロックをオフセットの昇順に辿り、最初に収まる空きブロックの先頭を返します。

`cplat_hashtable_add` と `cplat_hashtable_insert_direct` は、キーと値をそれぞれ独立に確保します。  
どちらか一方でも収まらなければ、テーブルを変更せずに `CPLAT_ERR_STORAGE_FULL` を返します。

### 更新時の自ブロックの扱い

`cplat_hashtable_update` などの更新は、対象レコードが現在使っているブロックも空きとみなして探索します。  
このとき、自ブロックと前後に隣接する空きブロックを 1 つの空きへ結合したうえで評価します。

探索は空きリストを変更しません。  
実際の確保は、呼び出し側が解放を済ませたあとの格納時に行います。  
探索、解放、格納の順に進むため、格納の時点では探索が前提とした状態が成立しています。

収まらなかった場合は解放も格納も行わないため、テーブルは変更されません。

### 圧縮の手順

`cplat_hashtable_compact` は次の順に処理します。

1. 空きブロックを辿り、使用中の連続区間を左へ詰めます。移動はオフセットの昇順に起きるため、上書きは生じません。
2. 空きブロックの長さを累積和へ置き換え、各 descriptor の移動量を二分探索で引けるようにします。
3. 各 descriptor の `offset` から、自分より前にある空きブロックのバイト数を引きます。
4. 未使用領域を 0 埋めし、空きリストを 1 要素へ戻します。

追加の作業領域を必要としません。

### 配置が変わる操作

格納済みブロックの配置が変わるのは、次の操作です。

- `cplat_hashtable_compact` - 同一のストレージ内で詰め直します。
- `cplat_hashtable_resize` - 残すレコードを移行先の領域へ 1 件ずつ書き直します。
- `cplat_hashtable_rebuild_into` - 同上です。
- 自動拡張版の書き込み - 新しい内部領域へ全レコードを移し、要求された書き込みを適用します。

確保は空き領域だけを使うため、対象レコード以外のブロックを動かしません。  
`cplat_hashtable_update` などは、対象レコード自身のブロックだけを再配置しえます。

容量を縮める場合も詰め直しは同じで、詰めた結果が新しい容量へ収まらなければ `CPLAT_ERR_STORAGE_FULL` です。

## 整合性検査

`cplat_hashtable_validate` は、空きリストについて次を確かめます。

- 要素数が `capacity + 1` 以下であること
- 長さが 0 でなく、`[0, storage_size)` の内側であること
- オフセットが昇順であること
- 隣接する空きブロックが結合済みであること
- 空きブロックの長さの合計が `storage_size` から使用バイト数を引いた値と一致すること
- 各使用中ブロックが、いずれの空きブロックとも重ならないこと

`cplat_hashtable_attach` は、走査が領域外へ出ないよう、要素数の上限だけを先に検査します。

使用中ブロック同士の重なりは検出しません。  
検出するには領域サイズに比例したビットマップか descriptor の整列が必要で、検査の計算量が変わるためです。  
この点は空きリストの導入前から同じです。

## メモリ コスト

空きリストは、可変長ストレージ 1 個あたり `16 × (capacity + 1)` バイトを占めます。

| 構成 | capacity 1024 | capacity 4096 |
| --- | --- | --- |
| 可変長キーのみ | 約 16 KiB | 約 64 KiB |
| 可変長キーと可変長値 | 約 32 KiB | 約 128 KiB |

固定長フィールドだけの構成では領域を確保しません。

`cplat_hashtable_required_size` と `hashtable-required-size` コマンドの出力には、この分が含まれます。  
外部バッファーを使う場合は、これらで必要バイト数を求めてください。

## 性能特性

`prod/src/cmd/bench-hashtable` で測定します。  
測定軸と実行手順は [ベンチマークの測定方法](../../../src/cmd/bench-hashtable/benchmark-method.md) を参照してください。

測定環境は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| CPU | Intel Xeon Gold 6254 @ 3.10GHz |
| OS | Red Hat Enterprise Linux 8.10 (WSL2、カーネル 6.6.87.2) |
| コンパイラ | GCC 8.5.0、`-O2` |
| 測定日 | 2026-08-22 |

1 件あたりの所要時間 (ナノ秒) は次のとおりです。

| 操作 | 256 | 1024 | 4096 | 16384 |
| --- | --- | --- | --- | --- |
| `fill` | 608 | 577 | 579 | 581 |
| `update` | 427 | 463 | 445 | 452 |
| `churn` | 635 | 742 | 1168 | 2959 |
| `compact` | 56 | 62 | 66 | 72 |
| `resize` | 367 | 420 | 434 | 456 |

`fill`、`update`、`compact`、`resize` は `capacity` によらずほぼ一定です。  
全体としては `capacity` に比例します。

### 断片化した状態の振る舞い

`churn` だけは `capacity` に比例して伸びます。  
1 件おきに回収した状態、すなわち空きブロックが `capacity` / 2 個ある状態からの確保だからです。

先着適合は空きブロックを先頭から辿るため、1 件あたりの所要時間は H に比例します。  
既存ブロックを動かさない方式のため、この振る舞いは避けられません。

対処は `cplat_hashtable_compact` です。  
圧縮すると H が 1 に戻り、以降の確保は再び実質 O(1) になります。

断片化しやすい使い方では、`CPLAT_ERR_STORAGE_FULL` を受けてから圧縮するのではなく、区切りのよい時点で圧縮することを検討してください。

## 設計上の判断

### 確保時に既存ブロックを移動しない

満杯に近づいたときへ内部で圧縮を挟めば、確保は償却 O(1) になり、実装も小さく収まります。

採用しませんでした。  
確保が既存ブロックを移動すると、`cplat_hashtable_find_value_ref` と `cplat_hashtable_get_key_ref` が返した参照が `cplat_hashtable_add` や `cplat_hashtable_update` で無効化されます。  
参照の有効期間を狭める契約変更になるため、利用側が圧縮の時期を決められる現在の形を維持しています。

この判断の代償が、前節の `churn` の振る舞いです。

### 空き領域そのものへリストを埋め込まない

空き領域へ `{next, size}` を書き込めば、追加の領域なしで連結リストを作れます。

採用しませんでした。  
理由は 2 つあります。

第一に、ノードを置けない大きさの空きブロックが残ります。  
可変長文字列は短いものが多く、ノード サイズ未満の空きブロックは珍しくありません。  
これらを表現できないと、確保できる組み合わせが減ります。

第二に、解放したバイトを 0 埋めする性質と両立しません。

### descriptor へオフセット順のリンクを持たせない

`hashtable_string_ref` へ「オフセット順で次のブロック」を足せば、追加は `capacity` × 8 バイトで済み、空きリストの半分です。

採用しませんでした。  
先着適合は先頭から辿る必要があるため、確保は使用中ブロック数に比例したままです。  
断片化のない充填でも、収まる隙間が常に末尾になるため、全体では `capacity` の 2 乗になります。

### 要素を 32 ビットにしない

要素を `{uint32, uint32}` の 8 バイトにすれば、メモリ コストは半減します。

採用しませんでした。  
`storage_size` に 4 GiB の上限が生じるうえ、`hashtable_string_ref` が `uint64` である形式との一貫性が崩れるためです。

## 改定の経緯

空きリストの導入前は、空き領域を表すデータを持たず、確保のたびに全 descriptor から空きを導出していました。

隙間を 1 つ進めるたびに `capacity` 件を走査するため、1 回の確保は最悪 O (N²) でした。  
削除がなければブロックは先頭から詰まるため、i 件目の追加は既存 i ブロックを辿ります。  
`capacity` 件の充填の合計は約 `N³ / 2` で、テーブルを埋めるだけで `capacity` の 3 乗を要していました。

圧縮も、詰め直すブロックを毎回選び直す選択ソート相当で O (N²) でした。  
`cplat_hashtable_resize` と `cplat_hashtable_rebuild_into` は全レコードを書き直すため、同じ次数を踏んでいました。

改定前後の所要時間 (5 試行の中央値、単位はミリ秒) は次のとおりです。

| 操作 | capacity 256 改定前 | 改定後 | capacity 1024 改定前 | 改定後 |
| --- | --- | --- | --- | --- |
| `fill` | 120.447 | 0.156 | 7656.482 | 0.590 |
| `update` | 15.825 | 0.109 | 999.811 | 0.474 |
| `churn` | 61.006 | 0.081 | 3885.230 | 0.380 |
| `compact` | 0.463 | 0.014 | 7.348 | 0.063 |
| `resize` | 235.149 | 0.094 | 15219.464 | 0.430 |

改定前は `capacity` を 4 倍にすると所要時間が約 64 倍になりました。  
`capacity` 4096 以上は現実的な時間で測定できないため、表には載せていません。

### 互換性

空きリストの導入で配置の版番号を 3 から 4 へ上げました。  
`cplat_hashtable_attach` は版番号の異なる領域を拒否するため、旧版で作った永続化領域は読み戻せません。

必要バイト数も増えます。  
外部バッファーを使う利用側は、`cplat_hashtable_required_size` で取り直してください。

確保が返すオフセットは改定前と同じです。  
昇順かつ結合済みの空きブロックを先頭から辿る列は、改定前が隙間を辿る列と一致するためです。  
成功と失敗の判定も変わりません。
