# C ランタイム抽象 (crt) 機能仕様

## 概要

C ランタイム抽象は、標準 C ライブラリと OS のファイル操作を、Linux と Windows で同じ呼び出し方にそろえた層です。  
対象は `cplat/crt/` の公開ヘッダー群で、標準入口は `cplat/crt/crt.h` です。

本書は、この層が満たす要件と、その解決策として用意した機能を説明します。  
生の関数と cplat の代替の対応表は [cplat API チート シート](../api-cheatsheet.md)、直接使用を禁じる関数の規範は [cplat コーディング規範](../coding-guideline.md) にあります。

## 解決する課題

標準 C ライブラリは、同じ処理を書いても Linux と Windows で結果が変わります。

- パス文字列の文字コードが異なります。Windows のナロー文字 API は UTF-8 を受け取りません。
- パスの区切り文字が異なり、Windows API は出力に `\` を混在させます。
- ファイルの共有モードの既定が異なり、Windows では開いている間の再オープンが失敗します。
- ファイル オフセットの型が異なり、32 ビットのままでは 2GB を超えるファイルを扱えません。
- 再入可能版と安全版の関数名が異なり、`gmtime_r` と `gmtime_s`、`strtok_r` と `strtok_s` のように書き分けが要ります。

さらに、標準関数の一部は、書き込み先の容量を受け取らない、失敗を通知しない、切り詰めを検出できないという設計上の欠陥を持ちます。  
これらは移植性の問題ではなく、どちらのプラットフォームでも同じ危険を生みます。

本層は、前者を差異の吸収として、後者を代替 API の提供として引き受けます。

## 要件と機能の対応

| 要件 | 解決する機能 |
|---|---|
| 境界外書き込みを呼び出し規約で防ぐ | 宛先の容量を必ず受け取る文字列・書式化 API |
| 切り詰めと失敗を見落とさない | 切り詰めを結果コードで通知する書式化と行入力 |
| 変換の失敗と範囲超過を検出する | 完全消費を検査する数値変換 |
| パスを文字コードの差なしに扱う | UTF-8 パスの受け取りと、Windows でのワイド文字変換 |
| パスの区切りを一意にする | 入力での正規化と、出力での `/` への統一 |
| ファイルの共有の既定をそろえる | Windows での共有モード指定を内包したオープン |
| 2GB を超えるファイルを扱う | 64 ビットのオフセットと位置 |
| 再入可能な時刻変換を書き分けずに使う | 再入可能版へ委譲する時刻変換 |
| ロケールに依存しない比較を行う | ASCII だけを畳む大文字小文字を無視する比較 |
| パスを組み立ててから開く手間を省く | 書式指定でパスを与える `_fmt` 系 API |
| OS のファイル ハンドルを直接扱う | `HANDLE` と `fd` を共通化した低レベル ファイル I/O |
| 一時ファイルを衝突なく作る | 一意な名前で作成する一時ファイル API |
| OS 由来の失敗理由を取得する | 詳細エラーの出力引数 |

## 危険な標準関数の代替

`strcpy` や `sprintf` のように宛先の容量を受け取らない関数は、呼び出し側がどれだけ注意しても境界外書き込みを防げません。  
本層は、これらに対して宛先の容量を必ず引数に持つ代替を提供します。  
容量を渡さずに呼ぶ書き方が成立しないため、検査の漏れが呼び出し時点で分かります。

`atoi` のように失敗を通知しない変換関数は、入力が不正でも 0 を返します。  
代替の変換 API は、文字列全体を消費したかどうかと範囲超過を検査し、結果コードで通知します。

`snprintf` と `fgets` は境界を検査しますが、切り詰めと終端の検出を呼び出し側の戻り値検査に委ねています。  
代替 API は切り詰めを結果コードとして返すため、検査を省略した実装が成立しません。

どの関数を禁止し、どの代替を使うかの規範は [cplat コーディング規範](../coding-guideline.md)、対応表は [cplat API チート シート](../api-cheatsheet.md) にあります。

## パスの扱い

パス文字列は、すべてのプラットフォームで UTF-8 として受け取ります。  
Windows では内部でワイド文字へ変換し、ワイド文字版の API を呼びます。  
呼び出し側は、現在のコード ページや `setlocale` の状態を考える必要がありません。

パスの区切りは、すべてのプラットフォームで `/` に統一します。  
Windows では入力の `\` も受け付け、必要に応じて内部で `/` へ正規化します。  
Windows API が返す `\` は、呼び出し側へ返す前に `/` へ正規化します。  
環境変数や設定ファイルから得た外部由来のパスは、正規化する API で明示的にそろえられます。

パスからファイル名、ディレクトリ、拡張子を取り出す API だけは、この方針の例外です。  
コンパイラが生成する `__FILE__` のように、区切りが `\` のまま渡る文字列を扱う必要があるためです。  
詳細は `cplat/crt/path.h` を参照してください。

## ファイル操作の差異吸収

ファイルを開く API は、Windows で共有を許可する指定を内包します。  
Windows のナロー文字版 `fopen` は排他で開くため、同じファイルを開いている間の再オープンが失敗します。  
本層は Linux と同じ「共有可」を既定とし、プラットフォームによって成否が変わらないようにします。

ファイルのオフセットと位置は 64 ビットで受け渡します。  
Windows の `_lseeki64` と Linux の `lseek` の型差を吸収し、2GB を超えるファイルを分岐なしに扱えます。

`read` と `write` は、Windows では 1 回の呼び出しで扱える上限が `INT_MAX` バイトです。  
本層はこの上限を隠さず、超過分が切り詰められることを契約として明示します。  
上限を意識せずに全量を扱いたい場合は、呼び出し側で繰り返します。

低レベルのファイル I/O は、Windows の `HANDLE` と Linux の `fd` を共通のハンドル型で扱います。  
ファイルの最終更新日時は、秒精度の `stat` とは別に、サブ秒を含む標準時刻型で取得と設定ができます。

## 書式指定でパスを与える API

ログ ファイルのように、連番や日付を含むパスを組み立ててから開く場面は多くあります。  
本層は、書式と可変引数からパスを組み立てて開く `_fmt` 系 API を、対応する基礎 API と対で提供します。  
呼び出し側がパス用のバッファーを用意し、長さを検査し、基礎 API を呼ぶ 3 段階を、1 回の呼び出しにまとめられます。

`_fmt` 系は内部でパスを展開したうえで基礎 API を呼びます。  
基礎 API と実装ファイルを分けているため、`_fmt` 系のテストで下位の基礎 API をモックへ差し替えられます。

## その他の差異吸収

環境変数の取得は、Windows で MSVC が非推奨とする関数を避けた実装へ委譲します。  
値を格納するバッファーに NULL を渡すと、存在の確認だけを行えます。  
設定は呼び出し元のプロセスにだけ反映され、子プロセスや親プロセスへは伝わりません。

時刻の分解は、Linux の再入可能版と Windows の安全版へそれぞれ委譲します。  
呼び出し側は関数名の差を書き分けずに、スレッド セーフな変換を使えます。

大文字小文字を無視する比較は、ASCII の範囲だけを畳みます。  
`setlocale` の状態によって結果が変わらないため、識別子やオプション名の比較に使えます。

Windows では、UTF-8 とワイド文字列を相互変換する API を提供します。  
Linux ではこのヘッダーは何も宣言しないため、利用側は Windows 専用の処理としてのみ呼び出します。

## 戻り値の規約

本層の API には、共通結果コードを返すものと、元の標準関数の戻り値規約を保つものがあります。  
既存のコードを機械的に置き換えられるようにするため、`fopen` のように戻り値そのものが結果である関数は、規約を保存します。

規約を保存する API も、OS 由来の失敗理由は詳細エラーの出力引数へ格納します。  
呼び出し側は、`errno` と `GetLastError()` を書き分けずに理由を取得できます。

どちらの規約に従うかは、各関数の Doxygen に明記します。  
共通結果コードの体系は [基盤 (base) 機能仕様](base.md) を参照してください。

## 適用範囲外

次の項目は本層が扱いません。

- 両プラットフォームで挙動が同じで、境界検査の欠落もない関数。`memcpy` や `strcmp` にラッパーは作りません。
- ディレクトリの走査。一覧の列挙 API は提供しません。
- 文字コードの一般的な変換。UTF-8 とワイド文字の相互変換だけを Windows 向けに提供します。
- ロケールに依存する文字列比較と大小関係。

## 前提と制約

パス文字列は UTF-8 であることを前提とします。  
現在のコード ページのナロー文字列を渡した場合の動作は保証しません。

パスの長さは `PLATFORM_PATH_MAX` を上限とします。  
`_fmt` 系 API は、この長さのバッファーへパスを展開します。

環境変数の設定は呼び出し元プロセスに閉じます。

## 選択の指針

ファイルの読み書きに、標準 I/O のラッパーとメモリ マップド ファイルのどちらを使うかは、アクセス パターンとファイル サイズで決まります。  
測定に基づく選定基準は [ファイル入出力 API の選定基準](../fileio-api-selection-guideline.md) を参照してください。

パスを固定文字列で与える場合は基礎 API を、組み立てが必要な場合は `_fmt` 系を使います。
