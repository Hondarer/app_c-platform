# ライブラリのカタログを外部へ公開する設計

> [!NOTE]
> 本書は、ライブラリが持つ文字列カタログを、そのライブラリの外部から利用できるように公開するための提案文書です。
> トレース種別の設計については、[トレース種別の文字列カタログの設計](string-catalog-trace-kind-design.md) を参照してください。
> app 固有の文脈引数については、[app 固有の文脈引数の設計](string-catalog-context-extension-design.md) を参照してください。
> 現行仕様については、[文字列カタログの機能仕様](../functional-spec/string_catalog.md) を参照してください。

## 目的

本設計は、ライブラリが持つ文字列カタログの生成物を、そのライブラリの公開 API の一部として外部へ提供できるようにします。  
利用側は、ライブラリが定義した文字列キーと型付きラッパーを使用して、文字列の組み立てとトレースの出力を要求できます。

公開する識別子の範囲と、外部との契約になる要素を明確にします。  
ライブラリの版が変わっても利用側のバイナリが壊れない条件を、生成器の検査として実装できる形で定めます。

## 解決する課題

現在の生成物は、1 つの実行ファイルまたは 1 つのライブラリの内部で使用することを前提としています。  
生成する関数の宣言にエクスポート装飾がないため、Windows では DLL の外部から参照できません。

文字列キーの列挙値は、カタログ定義の並び順から 1 始まりで生成器が決定します。  
外部へ公開した場合、この値は利用側のバイナリへ埋め込まれます。  
定義の途中へ項目を挿入すると値がずれるため、ライブラリだけを差し替えた利用側が、通知なく別の文字列を参照します。

型付きラッパーは `static inline` であり、利用側のコンパイル単位で展開されます。  
現在のラッパーは `cplat_string_catalog_format()` を直接呼び出し、`@MODULE@_catalog()` が返すカタログ オブジェクトを渡します。  
そのため利用側は、cplat へのリンクと、`cplat_string_catalog` 構造体のレイアウトへの依存を持つことになります。

## 適用範囲

本設計の対象範囲は、公開する識別子の範囲、エクスポート装飾の出力、文字列キーの値の固定、生成物の出力先、利用側の前提条件、および外部との契約になる要素です。

次の事項は、本設計の対象外とします。

- `cplat_string_catalog_entry` および `cplat_string_catalog` の構造体の変更 (レイアウトを維持するため)
- カタログをプロセス間または言語をまたいで共有する仕組み (C の共有ライブラリの境界だけを対象とするため)
- ライブラリの版の表明と照合の仕組み (app の配布方法に依存するため)

## 設計の方針

### 型付きラッパーの呼び先を簡易関数へ変更する

文字列リソース種別の型付きラッパーは、現在 `cplat_string_catalog_format()` を直接呼び出しています。

```c
static inline int sample_messages_key_file_open_failed(char *dest, const size_t dest_size, const char *file_path,
                                                       const int error_code)
{
    return cplat_string_catalog_format(sample_messages_catalog(), dest, dest_size,
                                       SAMPLE_MESSAGES_KEY_FILE_OPEN_FAILED, file_path, error_code);
}
```

この形式では、ラッパーを展開する利用側が 2 つの依存を持ちます。  
1 つは `cplat_string_catalog_format` へのリンク、もう 1 つは `@MODULE@_catalog()` が返す構造体のレイアウトです。

呼び先を、同じ生成物が提供する簡易関数 `@MODULE@_format()` へ変更します。

```c
static inline int sample_messages_key_file_open_failed(char *dest, const size_t dest_size, const char *file_path,
                                                       const int error_code)
{
    return sample_messages_format(dest, dest_size, SAMPLE_MESSAGES_KEY_FILE_OPEN_FAILED, file_path, error_code);
}
```

`@MODULE@_format()` はカタログ オブジェクトをライブラリの内部で補うため、利用側は構造体を参照しません。  
可変長引数の転送が 1 段増えますが、引数の個数と型の検査はラッパーのプロトタイプが行うため、検査の強さは変わりません。

この変更は、公開しないカタログにも同じく適用します。  
トレース種別はすでに `@MODULE@_write()` を経由しており、種別ごとに呼び先の規則が異なる状態を残さないためです。

### 公開する API の範囲を選べるようにする

生成物の関数を、戻り値が cplat の構造体を指すかどうかで 2 つに分けます。  
構造体を指す関数を公開すると、利用側が cplat の構造体レイアウトに依存するためです。

公開範囲は `api` と `full` の 2 つとし、カタログ定義で選びます。

| 識別子 | 戻り値が構造体を指す | `api` | `full` |
|---|---|---|---|
| `@MODULE@_format` / `@MODULE@_vformat` | いいえ | 公開 | 公開 |
| `@MODULE@_category` / `@MODULE@_id` / `@MODULE@_note` | いいえ | 公開 | 公開 |
| `@MODULE@_entry_count` | いいえ | 公開 | 公開 |
| `@MODULE@_write` / `@MODULE@_set_tracer` / `@MODULE@_get_tracer` | いいえ | 公開 | 公開 |
| `@MODULE@_catalog` / `@MODULE@_entry` | はい | 非公開 | 公開 |
| `@MODULE@_entries` / `@MODULE@_key_index` / `@MODULE@_key_index_count` | はい | 非公開 | 公開 |
| `@MODULE@_verify` | いいえ | 非公開 | 公開 |

`@MODULE@_verify` を `api` で公開しない理由は、カタログの自己点検が提供元の責務であるためです。  
ライブラリは、自身の初期化で点検を済ませた状態で利用側へ機能を提供します。

型付きラッパーと関数形式マクロは `static inline` およびプリプロセッサの定義であり、シンボルを持ちません。  
公開範囲によらず、生成ヘッダーを取り込んだ利用側がそのまま使用できます。

### 文字列キーの値を定義で固定する

公開するカタログでは、カタログ項目へ `value` を必須とします。  
生成器が並び順から値を決めると、定義の途中への挿入が、利用側のバイナリに対する非互換の変更になるためです。

```jsonc
{
    "key": "POTR_TRACE_KEY_SESSION_OPENED",
    "value": 1,
    "id": "POTR_TRACE_ID_0001",
    ...
}
```

生成器は、値が 1 以上であること、および重複がないことを検査します。  
値が連続していない場合、添字テーブルの該当位置へ `@MODULE_UPPER@_KEY_INDEX_ABSENT` を格納します。  
欠番を表す機構は生成物にすでにありますが、現在の生成器は値が連続する前提で添字を出力しているため、この出力を欠番に対応させます。

削除した項目の値は再利用しません。  
利用側の古いバイナリが持つ値が、別の文字列を指すことを防ぐためです。  
項目を廃止する場合は、定義から取り除いて値を欠番として残します。

公開しないカタログでは、`value` を引き続き省略できます。  
省略した場合の値の決め方は現在と同じです。

### エクスポート装飾を生成器が出力する

公開するカタログの関数宣言と定義へ、app のエクスポート マクロと呼び出し規約マクロを出力します。

```c
POTR_EXPORT int POTR_API porter_trace_write(int string_key, ...);
```

マクロの名前は、app の接頭辞から導出します。  
`cplat/base/dll_exports.h` の `CPLAT_DLL_EXPORT(prefix)` と `CPLAT_DLL_API(prefix)` が定める既存の規約と同じ形です。  
接頭辞が `POTR` であれば `POTR_EXPORT` と `POTR_API` になります。

生成物は、マクロを定義するヘッダーを取り込みます。  
`cplat` 以外のヘッダーを取り込むことになるため、生成物の依存に関する規範の解除が必要です。

### 設定を app 単位の設定ファイルへ集約する

エクスポート マクロの接頭辞と、マクロを定義するヘッダーは、app 内で共通です。  
[app 固有の文脈引数の設計](string-catalog-context-extension-design.md) で導入する app 単位のファイルへ、`export` 節として集約します。

同じファイルが文脈引数とエクスポートの両方を持つため、ファイルの役割を「文脈定義」から「カタログ設定」へ一般化します。  
カタログ定義からの参照も、`context` から `settings` へ改めます。

```jsonc
// app 単位のカタログ設定です。
{
    "export": {
        "prefix": "POTR",
        "header": "porter/porter_export.h"
    },
    "context": {
        "headers": ["porter/porter_spec.h"],
        "arguments": [ ... ]
    }
}
```

公開するかどうかはカタログごとに決まるため、カタログ定義へ `export` を記載します。

```jsonc
{
    "kind": "trace",
    "settings": "../catalog_settings.jsonc",
    "export": "api",
    "strings": [ ... ]
}
```

`export` を省略した場合は公開しません。  
`export` を記載して設定ファイルに `export` 節がない場合は、定義の誤りとして通知します。

## 生成物の出力先

公開するカタログのヘッダーは、ライブラリの公開ヘッダーの場所へ出力します。  
ソースはライブラリのソースの場所へ出力します。

| 生成物 | 出力先 | 取り込み方 |
|---|---|---|
| `@MODULE@.h` | `prod/include/<lib>/` | `#include <lib/module.h>` |
| `@MODULE@.c` | `prod/libsrc/<lib>/` | ライブラリのビルド対象 |

現在の生成器は、`--out-dir` が示す 1 つのディレクトリへ両方を出力します。  
ヘッダーの出力先を指定する `--header-dir` を追加し、省略した場合は `--out-dir` と同じ場所とします。  
Doxygen の `@file` が示す位置は、それぞれの出力先から導出します。

生成物を Git で管理しない方針は、公開するカタログでも変更しません。  
公開ヘッダーがビルドの成果物になるため、配布物へ含める手順を app 側で用意します。

## 利用側の前提条件

### cplat の実体をプロセスで 1 つにする

ライブラリと利用側は、cplat の同じ実体を共有します。  
出力する言語はプロセスで 1 つの設定として cplat が保持するため、実体が分かれると設定が二重化します。

静的リンクした cplat をライブラリと利用側がそれぞれ持つ構成は、想定しません。  
cplat を共有ライブラリとして配置し、双方がそれへリンクします。

### cplat へのリンクの要否

型付きラッパーの呼び先を簡易関数へ変更した後は、種別によって利用側の依存が異なります。

| 種別 | 利用側が取り込むヘッダー | 利用側から cplat の関数を呼ぶか |
|---|---|---|
| 文字列リソース | 生成ヘッダーと cplat の公開ヘッダー | 呼びません |
| トレース | 生成ヘッダーと cplat の公開ヘッダー | 呼びます |

トレース種別では、関数形式マクロが `cplat_path_basename(__FILE__)` を展開の位置で評価します。  
プロセス ID とスレッド ID の取得も `static inline` の内部で行うため、利用側のコンパイル単位に cplat の関数呼び出しが生じます。  
そのため、トレース種別を公開する場合は、利用側も cplat へリンクします。

文字列リソース種別では、利用側は生成物の簡易関数だけを呼びます。  
cplat の公開ヘッダーは型の定義のために取り込みますが、リンクは不要です。

### トレーサーの設定

公開したトレース種別のカタログは、ライブラリの内部に 1 つのトレーサーの設定を持ちます。  
出力先を決めるのは利用側であるため、`@MODULE@_set_tracer()` を公開し、利用側が初期化の段階で設定します。

共有ライブラリの内部の静的変数は 1 つであるため、境界をまたいでも設定は 1 か所に保たれます。  
ライブラリを静的リンクする複数のモジュールが同じプロセスに存在すると設定が分かれるため、共有ライブラリとして配置することを条件とします。

## 外部との契約になる要素

公開したカタログのうち、変更が利用側のバイナリへ影響する要素を次に示します。

| 要素 | 契約 | 変更したときの影響 |
|---|---|---|
| 文字列キーの値 | 固定する | 既存のバイナリが別の文字列を参照します |
| 文字列キーの名前 | 固定する | 利用側の再コンパイルが失敗します |
| 引数の個数と型 | 固定する | 利用側の呼び出しが不正になります |
| 分類値およびトレース レベル | 固定する | 出力の可否と重大度が変わります |
| `id` | 固定する | ログの検索と条件式の記述が一致しなくなります |
| 書式と備考の文言 | 固定しない | ライブラリの再ビルドだけで変更できます |
| app が定める文脈引数 | 固定する | 既存のバイナリが渡す可変長引数の個数と食い違います |
| 項目の追加 | 末尾へ追加する | 影響しません |

app が定める文脈引数の増減は、すべてのカタログ項目の可変長引数の並びを変えます。  
型付きラッパーは `static inline` であり、その並びは利用側のバイナリへ焼き込まれるため、ライブラリだけの差し替えでは値が食い違います。  
増減した場合は、利用側の再コンパイルが必要です。

引数の個数または型を変える必要が生じた場合は、既存の項目を変更せず、新しい値の項目を追加します。  
廃止する項目は定義から取り除き、値を欠番として残します。

## 生成器の変更

| 箇所 | 変更の内容 |
|---|---|
| 型付きラッパーの呼び先 | `cplat_string_catalog_format` から `@MODULE@_format` へ変更する |
| テンプレートの展開 | `@EXPORT@` と `@API@` を追加し、`expand()` の引数を増やす |
| 宣言と定義の出力 | 公開範囲に応じて装飾を付ける |
| 取り込むヘッダー | エクスポート マクロを定義するヘッダーを追加する |
| 文字列キーの値 | `value` を受け入れ、1 以上かつ重複がないことを検査する |
| 添字テーブル | 欠番の位置へ `KEY_INDEX_ABSENT` を出力する |
| 添字テーブルの検証 | 最後の項目の値ではなく、値の最大を基準にする |
| 出力先 | `--header-dir` を追加する |
| 設定ファイル | `export` 節を読み込み、`settings` の参照名へ改める |

生成器は 1 つのスクリプトのまま維持します。  
公開するかどうかは出力の装飾と検査の差であり、生成の流れは共通であるためです。

## 既存の規範との関係

`app/string-catalog-sample/AGENTS.md` は、生成物が依存してよいものを cplat の公開ヘッダーと標準ヘッダーだけと定めています。  
公開するカタログの生成物は、app のエクスポート マクロを定義するヘッダーへ依存するため、この規則の解除が必要です。

同じ規範は、型付きラッパーの名前が簡易関数と衝突しないことを求めています。  
呼び先を `@MODULE@_format` へ変更しても、この検査は現在と同じく必要です。

## 段階的実装計画

### 第 1 段階: 型付きラッパーの呼び先の変更

文字列リソース種別の型付きラッパーが、`@MODULE@_format` を呼ぶように変更します。  
生成器の単体テストと、`app/string-catalog-sample` の既存のテストで、組み立て結果が変わらないことを確認します。

### 第 2 段階: 文字列キーの値の固定

カタログ定義の `value` を受け入れ、重複と範囲を検査します。  
添字テーブルの欠番への対応と、検証の基準の変更を実装します。

### 第 3 段階: エクスポート装飾の出力

設定ファイルの `export` 節と、カタログ定義の `export` を実装します。  
公開範囲に応じた装飾の出力と、取り込むヘッダーの追加を行います。

### 第 4 段階: 出力先の分離

`--header-dir` を追加し、ヘッダーとソースを別の場所へ出力できるようにします。

### 第 5 段階: ライブラリでの確認

いずれかのライブラリでカタログを公開し、別の実行ファイルから利用する構成を用意します。  
Linux の共有ライブラリと Windows の DLL の双方で、シンボルが解決できることを確認します。

### 設計から変更した事項

設定ファイルの参照名を `settings` とし、公開範囲をカタログ定義の `export` に書く形は設計のとおりです。  
設定ファイルの置き場所は、本文で未決としていましたが、`app/string-catalog-sample` ではライブラリのカタログ定義と同じディレクトリに置きました。  
app 内で公開するカタログがライブラリに閉じており、参照を相対パス 1 語で書けるためです。

ライブラリの生成ソースは `prod/libsrc/samplecatalog/gen/` へ出力し、`GENDIR_EXTRA_C` でビルド対象へ登録しました。  
生成物を `gen/` へ置く既存の扱いに合わせ、ワークスペース共通の `.gitignore` がそのまま対象とするためです。  
公開ヘッダーは `prod/include/samplecatalog/` へ出力するため、app の `.gitignore` で個別に対象としました。

`value` の上限を 4095 としました。  
添字テーブルは最大の値までを網羅するため、上限がテーブルの大きさ (4096 要素、16 キロバイト) を決めます。

### 確認した事項

`app/string-catalog-sample` に `samplecatalog` ライブラリを新設し、2 つのコマンドで利用の形を分けました。

- `string-catalog-command-sample`: カタログをコマンドが同梱します (従来の `string-catalog-sample` を改名)
- `string-catalog-library-sample`: カタログをライブラリから受け取ります

Linux の共有ライブラリで、公開範囲 `api` が意図どおりに働くことを確認しました。  
`test/src/libsamplecatalog/exportTest` が、実際のエクスポート一覧とシグネチャを検査します。  
戻り値が構造体を指す関数と `_verify` が動的シンボル表に現れないことも、同じテストで確認しています。

Windows の DLL での確認は未実施です。

### 実装で判明した事項

型付きラッパーが `cplat_string_catalog_format()` を直接呼び、`<module>_catalog()` の戻り値を渡していたため、公開範囲 `api` の設計が成立しませんでした。  
ラッパーは利用側のコンパイル単位で展開されるため、構造体を返す関数を隠せなかったためです。  
第 1 段階として呼び先を簡易関数へ変更し、この依存を断ちました。

生成器の単体テストで、`unittest.main()` の呼び出しがファイルの中間にあり、それより後ろの 2 つのテスト クラスが実行されていませんでした。  
呼び出しを末尾へ移し、実行されるテストは 79 件から 131 件になりました。

## 検討事項

- **公開範囲の粒度**:  
  本書では `api` と `full` の 2 つを提案しています。  
  実際の利用で `full` が必要になるかは、条件式フィルターを利用側が構成する要求の有無によります。  
  必要がなければ `api` だけとし、構造体を返す関数を常に非公開にする選択肢があります。
- **確認のためのライブラリ**:  
  第 5 段階の確認をどの app で行うかを決める必要があります。  
  `app/porter` はすでに共有ライブラリとして構成されており、トレースの利用もあります。  
  一方で、サンプルとしての役割は `app/string-catalog-sample` にあり、そちらは実行ファイルだけの構成です。
- **`value` の必須化の範囲**:  
  本書では公開するカタログに限って `value` を必須としています。  
  公開しないカタログでも、定義の並べ替えで値が変わる性質は同じです。  
  すべてのカタログで必須とするかを決定する必要があります。
- **ライブラリの版との照合**:  
  文字列キーの値を固定しても、利用側がライブラリの版を確認する手段はありません。  
  カタログの内容から導いた識別子を公開し、利用側が起動時に照合する仕組みを設けるかを決定する必要があります。
- **文字列リソース種別の言語設定**:  
  出力する言語はプロセスで 1 つの設定です。  
  ライブラリが返す文字列の言語を、利用側の設定と別にする要求が生じるかを確認する必要があります。
- **Doxygen の出力単位**:  
  公開するカタログの生成ヘッダーは、ライブラリの公開ヘッダーとして Doxygen の対象になります。  
  グループの構成をライブラリ側の構成へ合わせるかを決定する必要があります。
