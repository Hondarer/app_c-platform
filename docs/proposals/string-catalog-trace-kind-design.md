# トレース種別の文字列カタログの設計

> [!NOTE]
> 本書は、文字列カタログへトレース ログ用の種別を追加するための提案文書です。  
> 現行仕様については、[文字列カタログの機能仕様](../functional-spec/string_catalog.md) および公開ヘッダー [string_catalog.h](../../prod/include/cplat/string_catalog/string_catalog.h) を参照してください。  
> 条件式による絞り込みについては、[文字列カタログの条件式フィルターの設計](string-catalog-filter-design.md) を参照してください。
> 利用 app が文脈引数を追加する方法については、[app 固有の文脈引数の設計](string-catalog-context-extension-design.md) を参照してください。

## 目的

本設計は、トレース ログの出力要求を、文字列カタログの型付き組み立て関数と同じ呼び出し形式で記述できるようにします。  
呼び出し位置と実行文脈を呼び出しごとに機械的に付与し、条件式フィルターの判定対象として参照できるようにします。

文字列カタログをトレース ログ専用の機能にはしません。  
既存の文字列リソースとしての利用方法を変更せず、トレース ログ用の生成物を追加で出力できる構成とします。

## 解決する課題

現在、カタログから組み立てた文字列をトレースへ出力するには、利用側がバッファーを用意し、文字列の組み立てとトレース出力の 2 つの呼び出しを記述する必要があります。  
呼び出しの記述が 2 か所に分かれるため、文字列キーとトレース レベルの対応を利用側が維持することになります。

呼び出し位置の情報は `cplat_tracer_write` のマクロが付与しますが、付与されるのはソース ファイル名と行番号だけです。  
関数名、プロセス ID、スレッド ID は付与されません。

条件式フィルターは、書式を展開する前の引数値を判定の対象とします。  
呼び出し位置と実行文脈を引数として渡していない場合、これらを条件に含めた絞り込みを実行できません。

## 適用範囲

本設計の対象範囲は、位置指定の番号空間の拡張、カタログ定義の種別の追加、トレース種別が持つ文脈引数の内容、生成器が出力する型付きラッパーとマクロの形式、および文脈値を取得するために cplat へ追加する API です。

次の事項は、本設計の対象外とします。

- トレースの出力行への関数名、プロセス ID、スレッド ID の追加 (別途判断するため)
- 条件式の構文、コンパイル、および判定処理 ([条件式フィルターの設計](string-catalog-filter-design.md) の対象とするため)
- 分類値からトレース レベルへの対応付けの規約 (利用側の責務とするため)

## 設計の方針

### 文脈値をカタログの引数として扱う

呼び出し位置と実行文脈は、カタログ項目の引数として定義し、可変長引数として渡します。  
条件式フィルターが参照できるフィールドは `key`、`id`、`category`、および引数の値であり、引数として渡した値だけが判定の対象になるためです。

この方式では、フィルター側に予約フィールドを追加しません。  
`arg.source_file_name contains "parser"` のように、利用者が定義した引数と同じ構文で条件を記述できます。

文字列カタログは、これらの値を文字列および整数として保持するだけであり、意味を解釈しません。  
そのため、`string_catalog` モジュールから `trace` モジュールへの依存は発生しません。

### 文脈引数を通常の引数として扱う

呼び出し位置と実行文脈を保持する引数を、本書では文脈引数と呼びます。  
これは説明のための呼び分けであり、カタログの構造上は利用者が記載した引数と同じものです。

文脈引数のための専用の仕組みは設けません。  
引数の定義、引数種別、名前と説明、値の格納先、書式の位置指定のいずれも、従来の文字列リソースと同じ扱いです。  
`cplat_string_catalog_entry` と `cplat_string_catalog` は変更しません。

文脈引数の定義は、項目の引数配列へ生成器が他の引数と同じ形式で出力します。  
条件式フィルターと Doxygen は、名前と説明を持つ通常の引数として扱います。

### 位置指定の番号空間

書式の位置指定は、引数配列のインデックスをそのまま表します。  
利用者が記載した引数を 0 番から、文脈引数を 40 番から配置し、書式解析では番号の変換を行いません。

この配置のために、`CPLAT_STRING_CATALOG_ARGUMENT_MAX` を 32 個から 50 個へ拡張します。  
書式解析が受け付ける位置指定の桁数は 2 桁までであり、50 個は変更せずに収まります。

この値は書式展開 1 回あたりのスタック消費を決定します。  
値の配列は 1 要素 16 バイトのため、50 個では 800 バイトです。

条件式フィルターのインデックス参照 `arg[<n>]` も、書式と同じ番号を使用します。  
番号の規則を 1 つに統一し、定義と条件式で異なる番号を記載することを避けます。

### 未使用のインデックスの表現

利用者の引数が 40 個に満たない場合、その次の番号から 39 番までのインデックスには引数が割り当てられません。  
この状態を表すため、引数種別へ未使用を表す値 `CPLAT_STRING_CATALOG_ARGUMENT_KIND_UNUSED` を追加し、その値を 0 とします。  
既存の引数種別は 1 つずつ繰り上げ、`STRING` を 1 とします。

値を 0 とする理由は、要素を明示しない初期化子と、ゼロで初期化した領域が、そのまま未使用を表すようにするためです。  
未使用を末尾へ追加した場合、0 は `STRING` のままとなり、記載を省略した要素が文字列の引数として解釈されます。

この変更は既存の列挙値を変えるため、互換性を保ちません。  
引数種別を参照している箇所は列挙定数の名前で記述しており、再ビルドで追従します。  
生成物は Git の管理対象ではなく、ビルドのたびに生成するため、定義の変更は不要です。  
手動で定義したカタログを持つ単体テストは、同じ変更で見直します。

未使用のインデックスは、可変長引数から値を取り出しません。  
可変長引数の収集は未使用の要素を読み飛ばし、既存の `default` の分岐が返す定義の誤りとは区別します。

書式が未使用のインデックスを参照した場合は、書式の誤りとして扱います。  
書式展開の `default` の分岐が定義の誤りを返すため、この振る舞いは既存の実装のままです。

引数配列は 0 番から連続し、要素数は最後に使用するインデックスに 1 を加えた値です。  
トレース種別では文脈引数の末尾が 45 番のため、項目ごとの引数配列は 46 要素になります。

可変長引数は引数配列の順序で渡します。  
利用者の引数が先、文脈引数が後です。

### 書式への展開を当面行わない

文脈値は引数として渡しますが、言語別の書式からは参照しません。  
カタログ定義の `texts` へ `{40}` から `{45}` までの位置指定を記載しないことで、組み立てた文字列に文脈値が現れない状態にします。

この方式では、トレースの出力行の形式を変更しません。  
`trace` モジュールと既存の出力先の実装は、本設計では変更の対象外です。

文脈値を出力へ含める必要が生じた場合は、カタログ定義の `texts` へ位置指定を追加します。  
実装の変更を伴わずに、定義の変更だけで切り替えられます。

### トレーサーをカタログが保持する

生成物は、出力先のトレーサーをカタログ単位で保持します。  
`<module>_set_tracer()` で設定し、`<module>_get_tracer()` で取得します。出力の関数形式マクロは、トレーサーを引数に取りません。

呼び出しごとにトレーサーを渡すと、出力のたびに同じハンドルを引き回すことになり、記述の手間が利用者側に残るためです。  
テストでのトレーサーの差し替えは `<module>_set_tracer()` で行えます。

未設定のまま出力を要求した場合は、文字列の組み立ても出力も行わず `CPLAT_ERR_INVALID_ARGUMENT` を返します。  
`cplat_tracer_write_at()` は NULL のハンドルを受け取ると何もせず成功を返すため、そのまま渡すと設定の漏れが成功として隠れます。

## 文脈引数の仕様

トレース種別のカタログ項目は、次の 6 個の文脈引数を持ちます。  
これらの引数定義は生成器が出力するため、カタログ定義へ記載しません。

| 位置指定 | 引数名 | 引数種別 | 値の取得元 |
|---|---|---|---|
| `{40}` | `source_file_path` | `STRING` | `__FILE__` |
| `{41}` | `source_file_name` | `STRING` | `cplat_path_basename(__FILE__)` |
| `{42}` | `source_line` | `INT32` | `__LINE__` |
| `{43}` | `function_name` | `STRING` | `__func__` |
| `{44}` | `process_id` | `UINT32` | `cplat_process_get_pid()` |
| `{45}` | `thread_id` | `UINT32` | `cplat_process_get_tid()` |

### ソース ファイル名の取得方法

C17 の標準は、ファイル名だけを展開する定義済みマクロを持ちません。  
標準が定めるのは `__FILE__` であり、その内容はコンパイラへ渡したソース ファイルの表記と一致します。

`__FILE_NAME__` は GCC 12 以降と Clang 9 以降が提供する拡張であり、標準ではありません。  
本リポジトリの Linux 側のコンパイラは GCC 8.5.0 であり、この拡張を使用できません。  
MSVC も同等のマクロを提供しません。

そのため、ファイル名の取得には既存の `cplat_path_basename()` を使用します。  
この関数は文字列の走査だけを行い、メモリの確保を伴いません。

makefw のビルド規則はソース ファイルをカレント ディレクトリからの相対表記で渡すため、Linux と GCC の組み合わせでは `source_file_path` と `source_file_name` が同じ値になります。  
ビルド方法を変更した場合やコンパイラが絶対パスを展開する場合に、両方の表記で条件を記述できるようにするため、2 つの引数を保持します。

### 関数名と引数の上限

`__func__` は C17 と C++11 の双方で使用できるため、処理系ごとのマクロは設けません。  
本リポジトリの C は C17、C++ は GCC と MSVC の双方で C++11 以降を使用します。

値の配列の要素数は `CPLAT_STRING_CATALOG_ARGUMENT_MAX` が決定します。  
本設計ではこれを 50 個へ拡張するため、利用者が記載できる引数は、文脈引数の先頭である 40 番の手前までの 40 個です。  
40 番から 49 番までの 10 個は文脈引数の領域とし、現在はそのうち 6 個を使用します。

## cplat への追加

### スレッド ID の取得

スレッド ID を取得する `cplat_process_get_tid()` を `cplat/runtime/process.h` へ追加します。  
同じ診断目的でプロセス ID を返す `cplat_process_get_pid()` と対になる API であり、`sync` モジュールが提供するスレッド ハンドルの操作とは用途が異なるためです。

戻り値の型は `uint32_t` とします。  
Linux の `gettid()` と Windows の `GetCurrentThreadId()` のどちらも 32 ビットの値を返し、既存の `cplat_process_get_pid()` の戻り値の型とも一致します。

Linux の実装は `syscall(SYS_gettid)` を直接呼び出します。  
glibc がラッパー関数 `gettid()` を提供するのは 2.30 以降であり、本リポジトリの Linux 側が使用する glibc 2.28 では宣言されないためです。

プロセス ID を取得する API は `cplat_process_get_pid()` としてすでに存在するため、追加しません。

### 取得コストの扱い

プロセス ID とスレッド ID は、トレースの出力要求ごとに取得します。  
取得のコストが問題になる場合は、スレッド ローカル記憶域へ保持する方式を検討します。  
判断は実測に基づいて行うため、本設計では最初の実装をシステム コールの直接呼び出しとします。

## 生成器の変更

### カタログ定義の種別

カタログ定義へ、種別を示す `kind` を追加します。  
値は `message` と `trace` の 2 つとし、省略した場合は `message` として扱います。  
既存のカタログ定義は変更せずに、従来どおりの生成物を出力します。

1 つのカタログ定義ファイルが 1 つのカタログに対応し、1 つのカタログが 1 つの種別を持ちます。

### 種別ごとの差分

| 観点 | `message` | `trace` |
|---|---|---|
| 生成物の出力先 | 呼び出し側のバッファー | トレーサーのハンドル |
| 呼び出し位置の付与 | 付与しない | マクロで付与する |
| 文脈引数 | 持たない | 引数配列の 40 番から 6 個を出力する |
| 分類値の記載 | `category` へ整数で記載する | `level` へ `cplat_trace_level` の名前で記載し、生成器が整数へ変換する |
| `id` | 省略できる | 必須とする |
| 生成物が参照するヘッダー | 文字列カタログの公開ヘッダー | 文字列カタログ、トレース、実行時支援の公開ヘッダー |

トレース種別で `id` を必須とする理由は、言語の設定によらず項目を識別できる文字列を、ログの検索と条件式の記述で使用するためです。

### 生成器の構成

生成器は `bin/string_catalog_gen.py` の 1 つのスクリプトとして維持します。  
JSONC の解析、引数種別の検査、位置指定の検査、インデックス テーブルの生成、Doxygen コメントの出力、および `clang-format` の適用は、種別によらず共通であるためです。

生成器の内部を、種別によらない処理と、種別ごとのラッパー出力処理へ分離します。  
生成器を 2 つのスクリプトへ複製すると、共通部分の修正が片方だけに適用される不整合が生じるため、複製は行いません。

## 生成物の構成

### カタログ定義の記載例

位置指定は文字列リソース種別と同じく `{0}` から始まります。  
文脈引数は定義へ記載せず、生成器が引数配列の 40 番から出力します。

```jsonc
{
    "kind": "trace",
    "author": "Tetsuo Honda",
    "date": "2026/09/20",
    "version": "1.0.0",

    "strings": [
        {
            "key": "SAMPLE_TRACE_KEY_FILE_OPEN_FAILED",
            "id": "SAMPLE_TRACE_ID_0002",
            "level": "ERROR",
            "brief": "ファイルのオープン失敗。",
            "arguments": [
                {
                    "kind": "STRING",
                    "name": "file_path",
                    "description": "開けなかったファイルのパス。"
                },
                {
                    "kind": "ERROR_CODE",
                    "name": "error_code",
                    "description": "errno または Win32 のエラー コード。"
                }
            ],
            "texts": {
                "neutral": "Failed to open file {0}. Error code={1}",
                "japanese": "ファイル {0} を開けませんでした。エラー コード={1}"
            },
            "notes": {
                "neutral": "The path is emitted as given by the caller."
            }
        }
    ]
}
```

### 生成するヘッダー

型付きラッパーは、呼び出し位置を引数として受け取る `static inline` 関数として出力します。  
マクロは、この関数へ呼び出し位置を渡すだけの入口として出力します。

```c
static inline int sample_trace_key_file_open_failed_with_source(
    const char *file_path, const int error_code, const char *source_file_path, const char *source_file_name,
    const int32_t source_line, const char *function_name)
{
    return sample_trace_write(SAMPLE_TRACE_KEY_FILE_OPEN_FAILED, file_path, error_code, source_file_path,
                              source_file_name, source_line, function_name, cplat_process_get_pid(),
                              cplat_process_get_tid());
}

#define sample_trace_key_file_open_failed(file_path, error_code)                      \
    sample_trace_key_file_open_failed_with_source((file_path), (error_code), __FILE__, \
                                                  cplat_path_basename(__FILE__), __LINE__, __func__)
```

プロセス ID とスレッド ID は、マクロではなく `static inline` 関数の内部で取得します。  
これらは呼び出し位置で確定する定数ではなく、実行時の値であるためです。

マクロを入口とする理由は、`__FILE__`、`__LINE__`、`__func__` が呼び出し位置で展開される必要があるためです。  
マクロは引数を `static inline` 関数へ渡すだけであり、引数の個数と型の検査は関数のプロトタイプによって行われます。

生成器は項目ごとの引数の個数を定義から確定できるため、マクロの仮引数も固定長で出力します。  
可変長引数マクロを使用しないため、`##__VA_ARGS__` の処理系ごとの差異を考慮する必要がありません。

### 生成するソース

トレースへの出力処理は、カタログ定義ごとに 1 つの関数として出力します。  
文字列を格納するバッファーを型付きラッパーごとに持つと、文字列キーの個数に比例してコードが増加するためです。

```c
int sample_trace_write(int string_key, ...)
{
    char text[CPLAT_STRING_CATALOG_TEXT_MAX];
    va_list arguments;
    int result;

    if (s_tracer == NULL)
    {
        return CPLAT_ERR_INVALID_ARGUMENT;
    }

    va_start(arguments, string_key);
    result = cplat_string_catalog_vformat(sample_trace_catalog(), text, sizeof(text), string_key, arguments);
    va_end(arguments);

    if (result != CPLAT_OK)
    {
        return result;
    }

    return cplat_tracer_write_at(s_tracer, (cplat_trace_level)sample_trace_category(string_key), NULL, text);
}
```

呼び出し位置を付与しない `cplat_tracer_write_at` を使用します。  
呼び出し位置はすでにカタログの引数として渡しており、トレース側で重ねて付与しないためです。

### 呼び出し側の記述

文字列リソース種別とトレース種別で、引数の並びが一致します。  
先頭の引数が、文字列の格納先かトレーサーのハンドルかという点だけが異なります。

```c
/* 文字列リソース種別 */
sample_messages_key_file_open_failed(text, sizeof(text), "config.json", 2);

/* トレース種別。出力先は事前に sample_trace_set_tracer() で設定する */
sample_trace_key_file_open_failed("config.json", 2);
```

## フィルター成立時の強制出力

条件式フィルターが成立した出力要求は、出力先のしきい値によらず出力します。  
絞り込みの条件を満たした記録が、レベルの設定によって失われることを避けるためです。

このために、`cplat_trace_level` へ通常のレベルと対になる強制出力のレベル帯を追加します。  
値は `CPLAT_TRACE_LEVEL_CRITICAL` より小さい負の値とし、`CPLAT_TRACE_LEVEL_FORCE_CRITICAL` を -7、`CPLAT_TRACE_LEVEL_FORCE_NONE` を -1 とします。  
通常のレベルとの相互変換は 7 の加減算だけで行えます。

| 定数 | 値 | 対応する通常のレベル |
|---|---|---|
| `CPLAT_TRACE_LEVEL_FORCE_CRITICAL` | -7 | `CPLAT_TRACE_LEVEL_CRITICAL` |
| `CPLAT_TRACE_LEVEL_FORCE_ERROR` | -6 | `CPLAT_TRACE_LEVEL_ERROR` |
| `CPLAT_TRACE_LEVEL_FORCE_WARNING` | -5 | `CPLAT_TRACE_LEVEL_WARNING` |
| `CPLAT_TRACE_LEVEL_FORCE_INFO` | -4 | `CPLAT_TRACE_LEVEL_INFO` |
| `CPLAT_TRACE_LEVEL_FORCE_VERBOSE` | -3 | `CPLAT_TRACE_LEVEL_VERBOSE` |
| `CPLAT_TRACE_LEVEL_FORCE_DEBUG` | -2 | `CPLAT_TRACE_LEVEL_DEBUG` |
| `CPLAT_TRACE_LEVEL_FORCE_NONE` | -1 | `CPLAT_TRACE_LEVEL_NONE` |

しきい値の判定は「出力要求のレベルがしきい値と同じかより重いこと」であり、しきい値が `CPLAT_TRACE_LEVEL_NONE` の場合だけ出力しません。  
強制出力のレベル帯は、どの通常のしきい値よりも小さいため、判定処理を変更せずに通過します。  
しきい値が `CPLAT_TRACE_LEVEL_NONE` の出力先へは出力しません。出力しない設定を明示している出力先まで越えないためです。

負の値とする理由は、既存の列挙値を変えずに追加できるためです。  
出力先ごとのしきい値を設定する API は、強制出力のレベル帯を受け付けません。  
しきい値として指定すると、強制出力の要求だけが通る状態になるためです。

トレースの出力行に記録するレベルの表記は、対応する通常のレベルと同じにします。  
強制出力であるかどうかは絞り込みの結果であり、記録の重大度ではないためです。

syslog、EventLog、ETW への変換では、強制出力のレベル帯を個別に扱えます。  
これらの出力先は、cplat の外側でも重大度による絞り込みを行うため、変換先の重大度を選べるようにしておきます。

## 条件式フィルターとの関係

条件式フィルターを適用する段階では、`cplat_string_catalog_vformat` の呼び出しを `cplat_string_catalog_vformat_filtered` へ置き換えます。  
置き換えの対象は、生成器が出力する `<module>_write` の内部だけです。

条件式が成立した呼び出しでは、分類値から変換したレベルを強制出力のレベル帯へ移してから `cplat_tracer_write_at` を呼び出します。

文脈引数は通常の引数であるため、[条件式フィルターの設計](string-catalog-filter-design.md) の「判定の事前計算」で定義した 3 つの状態をそのまま使用します。  
`arg.source_file_name` や `arg.thread_id` を条件に記述でき、フィルター側に変更は生じません。

文脈引数は引数配列の末尾に位置します。  
可変長引数は先頭から順にしか取り出せないため、文脈値だけを参照する条件であっても、手前にある利用者の引数を収集してから判定します。  
収集を省略できるのは、条件式が「常に不一致」と事前に判定できる場合だけです。

### 第 3 段階で設計から変更した事項

生成物の引数配列は、値を受け取らないインデックスを要素を明示しない形で埋めます。  
この形では名前と説明がヌル ポインターになるため、`cplat_string_catalog_verify` が値を受け取らない引数へ名前と説明を求めないよう変更しました。

型付きラッパーの説明文は、1 文ずつ改行して出力します。  
1 行に詰めると、整形時に `@c` と対象の名前の間で折り返されるためです。

### 第 3 段階で決定した事項

トレース種別の `texts` は、既存の種別と同じく全言語を許可します。  
運用者が読むログを日本語にする要求があるためです。

文脈引数は、ソース ファイルのパスとファイル名を両方持ちます。  
ビルド方法の変更や、絶対パスを展開するコンパイラに備えるためです。

条件式が成立した出力要求を、出力先のしきい値によらず出力します。  
方式は「フィルター成立時の強制出力」に記載しました。

### 第 3.5 段階で決定した事項

強制出力のレベル帯を syslog と ETW へ渡すとき、`FORCE_VERBOSE` と `FORCE_DEBUG` は `LOG_INFO` と Informational へ引き上げます。  
INFO 以上を常時記録の対象として設計しているため、その帯へ入れて cplat の外側の設定で捨てられないようにするためです。  
ほかの強制出力のレベルは、対応する通常のレベルと同じ重大度で渡します。

しきい値を設定する API は、通常のレベルの範囲外をすべて拒否します。  
強制出力の帯だけを拒否すると、範囲外の値との扱いが不揃いになるためです。

詳細度の選び方を、機能仕様、モジュールの README、公開ヘッダーへ明記しました。  
INFO 以上を常時記録の対象とし、量の多い記録や内部の状態の詳細は VERBOSE または DEBUG とします。

### 第 4 段階で解除した既存の規範

`app/string-catalog-sample/AGENTS.md` の 2 つの規則を、トレース種別に限って解除しました。  
分類値を定義ファイルへ整数で書く規則は、トレース種別では `level` へ名前で書く規則へ置き換えます。  
型付きラッパーを関数形式マクロにしない規則は、トレース種別では解除します。マクロは `static inline` の関数へ渡すだけであり、引数の個数と型の検査はその関数のプロトタイプが行うためです。

## 検討事項

- **ソース ファイルの 2 つの表記の要否**:  
  makefw の現在のビルド規則では、`source_file_path` と `source_file_name` が同じ値になります。  
  条件式フィルターは `ends_with` と `contains` を提供するため、`source_file_path` だけでもファイル名による絞り込みを記述できます。  
  呼び出しごとの引数を 1 個削減する選択肢として残します。
- **言語別の書式の許可範囲**:  
  トレース ログをニュートラル言語に固定すると、実行環境の言語設定によらずログの表現が一定になり、解析との突き合わせが容易になります。  
  一方で、運用者が読むログを日本語にする要求もあります。  
  トレース種別で `texts` にニュートラル言語だけを許可するか、既存の種別と同じく全言語を許可するかを決定する必要があります。
- **トレース レベルによる早期の打ち切り**:  
  現在の `cplat_tracer` は出力先ごとのしきい値を保持しますが、すべての出力先を通した実効的なしきい値を取得する API を持ちません。  
  出力対象にならない文字列に対して書式展開を省略する場合は、実効的なしきい値を取得する API の追加が必要です。
- **引数配列の大きさ**:  
  トレース種別では、項目ごとの引数配列が 46 要素になります。  
  1 要素 24 バイトのため 1 項目あたり約 1.1 キロバイトで、うち 38 要素までが未使用のインデックスです。  
  文脈引数の開始番号を下げると読み取り専用データを削減できますが、利用者が記載できる引数の個数も同じだけ減ります。
- **文脈引数の名前の重複**:  
  利用者が定義した引数と文脈引数の名前が重複した場合の扱いを決定する必要があります。  
  生成器が定義の検査で誤りとして通知する方針を想定しています。
- **文脈引数を持つ項目の既存 API での扱い**:  
  `cplat_string_catalog_format` を直接呼び出す利用者は、文脈引数の値を自分で渡すことになります。  
  型付きラッパーを経由しない呼び出しを許可するか、トレース種別では禁止するかを決定する必要があります。
- **既存の規範との整合**:  
  `app/string-catalog-sample/AGENTS.md` は、型付きラッパーを関数形式マクロにしないことと、生成物が分類値を解釈しないことを定めています。  
  トレース種別ではどちらの規則も変更が必要なため、規範の記述を更新する必要があります。
- **`mock_cplat` への追加**:  
  トレース種別の生成物は `cplat_tracer_write_at` を呼び出します。  
  利用側の単体テストで出力内容を検証する場合に、既存の `mock_cplat` のトレース用モックで対応できるかを確認する必要があります。
