# 実行時支援 (runtime) 機能仕様

## 概要

実行時支援は、プログラムが自分自身の実行環境を調べ、外部の実装を取り込み、終了処理をまとめるための機能群です。  
対象は `cplat/runtime/` の公開ヘッダー群で、ホスト情報、モジュール情報、プロセス、権限昇格、終了処理、動的シンボル解決、メモリ ロックに分かれます。

本書は、これらの機能が満たす要件と、その解決策としての機能を説明します。  
モジュール構成と使用例は `prod/libsrc/cplat/runtime/README.md`、メモリ ロックの詳細は [メモリ ロック API](../memory-lock.md) を参照してください。

## 解決する課題

共有ライブラリやプラグインを含む構成では、実行中のプログラムが次を知る必要があります。

- 自分がどのファイルからロードされたか
- プロセス本体の実行ファイルはどれか
- どのホストで動いているか

これらの取得方法は Linux と Windows で異なります。  
また、関数の実装を実行時に差し替える仕組み、権限昇格、確実な終了処理も、それぞれプラットフォーム固有の API が必要です。

本機能群は、これらを共通の API へまとめ、利用側が OS ごとの分岐を書かずに済むようにします。

## 要件と機能の対応

| 要件 | 解決する機能 |
|---|---|
| 動作中のホストを識別する | DNS ホスト名の取得 |
| 自分のモジュールの位置を知る | 関数アドレスからのモジュール パスと basename の取得 |
| プロセス本体の実行ファイルを知る | 実行ファイルの絶対パスの取得 |
| 子プロセスを起動して結果を得る | 起動、待機、終了コード取得、強制終了 |
| 管理者権限が必要な処理を実行する | 権限の確認と、必要に応じた昇格起動 |
| 昇格したプロセスの結果を呼び出し元へ返す | 一時ファイル経由の結果メッセージ受け渡し |
| 終了時に後始末を確実に行う | 終了コールバックの登録と、終了コードを渡す終了 API |
| 終了要求を捕捉して自前で処理する | 終了要求コールバックの登録 |
| 関数の実装を設定で差し替える | 設定ファイルに基づく動的シンボル解決 |
| 機密データのページ アウトを避ける | 自プロセスのメモリ ロック |

## ホストとモジュールの情報

ホスト名の取得は、Linux と Windows で API 名も文字コードも異なります。  
本機能は DNS ホスト名を UTF-8 で返す 1 つの API にまとめます。  
返る値は OS が保持する DNS ホスト名であり、完全修飾ドメイン名であることは保証しません。

モジュール情報は、関数アドレスを手掛かりに、その関数が属するモジュールの絶対パスと basename を返します。  
共有ライブラリが自分自身の名前を知る手段になるため、設定ファイル名やログの識別子を自分の名前から組み立てられます。  
basename は拡張子を取り除いて返すため、`<basename>_extdef.json` のような命名と組み合わせられます。

Windows では、関数アドレスから得られるモジュールは DLL を指すことがあります。  
プロセス本体の実行ファイルが必要な場合は、実行ファイルのパスを返す API を使います。  
サービス登録時の起動コマンドを組み立てる用途がこれに当たります。

## プロセスの起動と権限昇格

子プロセスの起動、終了待ち、終了コードの取得、強制終了、後始末を提供します。  
起動して終了まで待つだけの用途には、同期実行の API を使えます。

権限昇格は、プロセスの起動とは別の機能として分けています。  
権限確認と昇格起動の機能はプロセス機能を利用しますが、逆方向の依存はありません。  
権限が不要な用途がコンソール関連の機能まで引き込まないようにするためです。

昇格が必要な処理の入口では、必要に応じて昇格実行する API を呼びます。  
Windows では未昇格の場合に昇格を要求して自分自身を再起動し、Linux では実効ユーザー ID が root でなければ失敗します。

昇格したプロセスの出力を、呼び出し元のコンソールへ確実に表示する方法は 2 通りあります。  
1 つは親のコンソールへ再接続する方法ですが、再接続後に間欠的に書き込めなくなる事象を実機で確認しており、原因を特定できていません。  
確実に結果を表示する必要がある場合は、もう 1 つの方法である結果メッセージの受け渡しを使ってください。  
昇格プロセスはコンソールを引き継がず、結果を一時ファイル経由で返し、通常の権限で動作している呼び出し元がそれを表示します。

## 終了処理

プロセスの終了時に行う後始末は、登録した終了コールバックとして集約できます。  
登録したコールバックは、登録と逆の順序で 1 回だけ実行します。

終了コードを後始末の処理へ渡したい場合は、専用の終了 API を使います。  
`atexit()` の経路では、C 標準の制約により `exit()` の引数を取得できないためです。

終了要求を捕捉して自前で処理する場合は、終了要求コールバックを登録します。  
捕捉できない終了は保証の対象外です。  
強制終了、`_exit`、クラッシュが該当します。

## 動的シンボル解決

関数の実装を実行環境ごとに差し替えたい場合があります。  
本機能は、設定ファイルで指定したライブラリ名と関数名から、実行時に関数ポインターを解決します。

解決の対象は、静的に定義したエントリで宣言します。  
初回の解決でライブラリのロードとシンボルの探索を行い、結果をエントリへ保持するため、2 回目以降は探索を繰り返しません。  
ライブラリ名に拡張子は書かず、プラットフォームに応じた拡張子を内部で補完します。

設定ファイルは、関数のキーごとにライブラリ名と関数名を持つ JSON です。  
行コメントとブロック コメントを書けます。  
必須フィールドの欠落、型の不一致、未知のキー、ファイルの不在、解析の失敗は、いずれも無視します。  
設定の誤りでプログラムが起動しなくなるより、既定の実装へ落とす方が安全なためです。

解決に失敗した場合は関数ポインターが NULL になります。  
呼び出し側は、既定の実装を自分で持つ設計にしてください。

## メモリ ロック

暗号鍵やパスフレーズのように、ディスクへページ アウトさせたくないデータがあります。  
本機能は、自プロセスのメモリをページ アウトされにくくする API を提供します。

指定した範囲だけをロックする方法と、プロセスの現在のマッピング全体をロックする方法があります。  
後者は解除に必要な情報をスコープとして返し、呼び出し側は処理を終えた時点でスコープを解放します。

Linux の該当 API はプロセス全体の状態を変える一方、Windows には対応する単一の API がありません。  
このため、本機能は成功したスコープの数とロック範囲を内部で管理し、最後のスコープが解放された時点で実際の解除を行います。  
複数の箇所が独立にロックしても、途中の解放で他方のロックが失われません。

将来のマッピングを対象に含める指定と、ページ フォルト時にロックする指定は Linux だけで有効です。  
Windows では `CPLAT_ERR_UNSUPPORTED` を返します。

フラグの一覧、スタックの先行確保、結果コードの対応、プラットフォームごとの実装は [メモリ ロック API](../memory-lock.md) を参照してください。

## 適用範囲外

次の項目は本機能群が扱いません。

- 別プロセスのメモリのロック。対象は呼び出しプロセスのメモリだけです。
- 休止状態、クラッシュ ダンプ、ログ出力への機密データの流出防止。メモリ ロックはこれらを防ぎません。
- 捕捉できない終了経路での後始末。強制終了とクラッシュは保証の対象外です。
- プラグインの探索と列挙。動的シンボル解決は、設定に書かれたものだけを対象にします。

## 前提と制約

動的シンボル解決の初期化と解放は、共有ライブラリのロード フックとアンロード フックから呼ぶ前提です。  
解放はその前提に合わせて内部ロックを取りません。

差し替えた実装から元の関数を再帰的に呼ぶ構成は避けてください。

メモリ ロックの上限は OS の設定に従います。  
Linux では `RLIMIT_MEMLOCK` を超えるロックに追加の権限が必要です。
