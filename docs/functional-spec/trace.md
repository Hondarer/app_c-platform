# トレース (trace) 機能仕様

## 概要

トレースは、アプリケーションのログを、OS のログ基盤、ファイル、標準エラー出力へ同じ呼び出しから送る機能です。  
対象は `cplat/trace/` の公開ヘッダー群で、利用側の入口は `cplat/trace/tracer.h` の 1 本です。

本書は、この機能が満たす要件と、その解決策として用意した機能を説明します。  
API の詳細と使用例は `prod/libsrc/cplat/trace/README.md`、出力先ごとの制約は各バックエンドの README を参照してください。

## 解決する課題

運用ログを出す先は 1 つではありません。  
運用者は OS のログ基盤を見て、開発者は詳細な診断を見て、起動直後の確認は端末で行います。

これらを素直に実装すると、次の問題が起きます。

- OS のログ基盤の API がプラットフォームで異なります。Windows はイベント ログ、Linux は syslog です。
- 出力先ごとに必要な詳細度が違うため、1 つのしきい値では運用ログが詳細すぎるか、診断が足りないかのどちらかになります。
- ログ ファイルは放置すると際限なく増えます。
- 複数のプロセスが同じログ ファイルへ書くと、行が混ざるかローテーションが壊れます。
- 出力の呼び出しに毎回ファイル名と行番号を書くのは現実的ではありません。

本機能は、出力先の違いを 1 つのハンドルの下へまとめ、しきい値を出力先ごとに分けます。

## 要件と機能の対応

| 要件 | 解決する機能 |
|---|---|
| OS のログ基盤へ、プラットフォームを問わず出力する | イベント ログと syslog を同じ API へ束ねた OS トレース |
| 開発者向けの詳細診断を、運用ログと分けて出す | Windows の ETW を独立した軸として提供 |
| ログをファイルへ残す | ファイル出力と、サイズによる世代ローテーション |
| 起動直後の動作を端末で確認する | 標準エラー出力への 1 行テキスト出力 |
| 出力先ごとに詳細度を変える | 出力先ごとに独立したしきい値 |
| 運用中に詳細度を変える | 稼働中でも変更できるしきい値と、原子的な反映 |
| 出力位置をたどれるようにする | ファイル名と行番号の自動付与 |
| バイナリを目視できる形で残す | HEX テキストとしての書き込み |
| 複数のプロセスから同じファイルへ書く | プロセス間の調停を行う共有モード |
| 不要な同期コストを避ける | ハンドルごとに選べる並行処理の管理主体 |
| 出力を横取りして加工する | フックの登録とチェーンの継続 |

## 出力先

出力先は 4 つあり、それぞれ独立したしきい値を持ちます。

| 出力先 | 位置づけ | 既定のしきい値 |
|---|---|---|
| OS トレース | 運用者が参照する OS ネイティブの運用ログ | 無効 |
| ETW (Windows のみ) | 開発者向けの低オーバーヘッド診断チャネル | VERBOSE |
| ファイル | ローカルに残す運用ログ | INFO |
| 標準エラー出力 | 端末での即時確認 | 無効 |

OS トレースが既定で無効なのは、運用者のログ基盤へ出すかどうかが運用側の判断だからです。  
ETW が既定で有効なのは、購読するプログラムがいるときだけイベントが実体化するため、通常時のコストが小さいからです。

Windows のイベント ログは、利用前にイベント ソースの登録が必要です。  
イベント ソースは cplat 全体で共通のため、登録用のコマンドで一度だけ登録します。

Linux には ETW がありません。  
ETW のしきい値を設定する API は何もせず、取得すると常に無効を返します。

## トレース レベル

レベルは CRITICAL から DEBUG までの 6 段階と、その出力先を無効化する NONE です。  
各出力先は、設定したレベル以上に重大なメッセージだけを出します。

OS 側のレベル体系は cplat より粗いため、対応付けに丸めが入ります。  
syslog と ETW には VERBOSE より細かい標準レベルがないため、DEBUG は VERBOSE と同じ詳細度になります。  
Windows のイベント ログはエラー、警告、情報の 3 種のみのため、INFO、VERBOSE、DEBUG はいずれも情報になります。  
ただし後から分析できるように、レベルごとに異なるイベント ID とカテゴリを割り当てます。

ファイルと標準エラー出力は cplat のレベルをそのまま区別します。

## ライフサイクル

トレースは、設定するフェーズと出力するフェーズを分けます。

```text
create -> set_name / set_* -> start -> write -> stop -> dispose
```

生成した直後は停止状態で、設定を変更できます。  
開始したあとに書き込みを行い、停止すると再び設定を変更できます。  
破棄は、開始と停止のどちらの状態からでも行えます。

しきい値の変更だけは、開始中でも行えます。  
出力を止めずに詳細度を上げ下げできるようにするためです。  
変更は排他制御のもとで原子的に反映するため、旧しきい値と新しきい値の両方で出力対象になるメッセージを取りこぼしません。

識別名、ファイル名、フックの設定は停止中に限ります。  
これらは出力先そのものを組み替えるため、出力中の変更を許すと出力先が不定になります。

破棄にはハンドル変数のアドレスを渡し、破棄後は変数へ NULL を設定します。  
ハンドルが所有する同期オブジェクトを利用側が解放する必要はありません。

## 並行処理の管理主体

同一ハンドルへの並行呼び出しを、どちらが管理するかを生成時に選びます。

トレース側が管理する方式では、ハンドルごとに読み書きロックを生成し、複数スレッドから同じハンドルを呼べます。  
呼び出し側が管理する方式では、ハンドル専用のロックを生成しません。  
単一スレッドで使う場合や、呼び出し側に既存の排他制御がある場合に、余分な同期コストを避けられます。

後者では、同一ハンドルへの呼び出しが重ならないことを利用側が保証します。  
異なるハンドルを並行して生成、利用、破棄することは、どちらの方式でもできます。

## 書き込み

通常のメッセージと、バイナリを HEX テキストにしたメッセージを書き込めます。  
どちらも、書式と可変引数を取る版があります。

公開名の書き込み API は、ファイル名と行番号を自動で付与する関数風マクロです。  
呼び出しごとに位置情報を書く必要がありません。  
位置情報を付けずに生のメッセージを書く場合は、低レベル関数を直接呼びます。

タイムスタンプは、NULL を渡すと内部で現在時刻を取得します。  
明示した時刻を渡すと、ファイルと標準エラー出力の出力にその時刻を使います。  
明示した時刻が不正な場合も出力自体は継続し、内部で現在時刻へ代替したことを戻り値で通知します。

メッセージ長と HEX 出力には共通の上限があり、超えた分は安全な範囲で切り詰めます。

## ファイル出力

ファイル出力は、1 行ずつ追記し、サイズの上限に達すると世代を繰り上げてローテーションします。  
出力先のパスを設定しない場合は、実行ファイルのディレクトリ配下の既定パスへ出力します。

同じパスへ複数のプロセスが書く場合は、共有モードを指定します。  
共有モードでは、ローテーションをロック ファイルによるプロセス間排他のもとで実行します。  
指定しない場合は単一プロセス専用で、プロセス間の調停を行いません。  
このモードでは、他プロセスが同じパスへ書き込まないことを呼び出し側が保証します。

## テストからの観測

OS のログ基盤への出力は、テストから内容を確認しづらい経路です。
Linux の syslog 出力は、環境変数でファイル記述子を指定すると、同じメッセージをその記述子へも書き込みます。
テストは、そこを読むことで出力内容を検証できます。

この経路はテストの補助であり、製品の動作では使いません。

## フック

登録したフックは、書き込みのたびに呼ばれます。  
出力を別の経路へ送る、内容を検査するなどの用途に使えます。

複数のフックを登録した場合は、チェーンとして順に呼び出します。  
フックの中でチェーンを継続する API を呼ぶと次のフックへ進み、呼ばなければそこで止まります。

## 適用範囲外

次の項目は本機能が扱いません。

- ログの収集と転送。ネットワーク越しにログを送る出力先は提供しません。
- 構造化ログのスキーマ。メッセージは行のテキストとして扱います。
- ネットワーク ファイル システム上のログ ファイル。ファイル出力はローカル ファイル システム向けです。
- ログの解析と検索。

## 前提と制約

Windows でイベント ログを使う場合は、事前にイベント ソースの登録が必要です。

呼び出し側が並行処理を管理する方式では、同一ハンドルへの同時呼び出しを直列化してください。

識別名、ファイル名、フックの変更は停止中に限ります。  
稼働中に変更する場合は、いったん停止してから設定し、再度開始します。
