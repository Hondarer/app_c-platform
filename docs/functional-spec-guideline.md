# cplat 機能仕様の記載規範

## 概要

本書は、cplat の機能仕様に記載する内容、章立て、記載粒度、要件 ID と UUID の運用を定めます。  
対象は `docs/functional-spec/` 配下の機能仕様です。

機能仕様は、cplat に割り当てられた要件を、API 設計、実装設計、実装、テストへ渡すための入力です。  
機能仕様より下流の成果物を根拠として、機能仕様を記載してはなりません。

本文の構成と表現は、[日本語技術文書の文章規範](../../../framework/docsfw/docs/japanese-technical-writing-guideline.md) に従います。

## 機能仕様の役割

機能仕様は、利用側または上位設計から見た cplat の責務を定めます。  
cplat が提供する能力、外部から観測できる振る舞い、利用条件、保証範囲、適用範囲外を記載します。

機能仕様は、関数の一覧や実装の解説ではありません。  
関数の構成と契約、実装方式、検証方法は、機能仕様から導出する下流成果物が定めます。

## 記載する内容

機能仕様には、次の内容を記載します。

- cplat が解決する、利用側の課題
- cplat 自身が満たす機能、品質、互換性、方式の要件
- 入力の種類、処理の結果、状態の変化など、利用側から観測できる振る舞い
- Linux と Windows で利用側から見える結果が異なる場合の差
- データ形式、文字モデル、暗号方式など、相互運用性または安全性のために固定する条件
- 利用側が満たす前提と、cplat が保証する範囲の限界
- cplat が扱わない範囲と、cplat 内に代替機能がある場合の選択方法

外部標準または OS の仕様は、要件の条件や互換性を定義するために必要な場合だけ参照できます。  
参照する場合は、cplat が満たす内容を本文で明示し、外部文書だけに要件を委ねてはなりません。

## 記載しない内容

機能仕様には、次の内容を記載しません。

- cplat を利用するアプリケーションの業務要件、運用、配備、監視、教育
- 関数名、型名、定数名、関数の引数と戻り値
- 公開ヘッダー、ソース ファイル、実装ディレクトリの構成
- 使用する外部ライブラリ、内部データ構造、内部アルゴリズム
- コーディング規則、API の命名規則、実装手順
- テスト ケース、テスト用の観測経路、検証コマンド
- API の移行表、使用例、チュートリアル

特定の方式を採用すること自体が相互運用性または安全性の要件である場合は、その方式を「制約」として記載できます。  
この場合も、方式を実現するライブラリや内部処理は記載しません。

未解決の実装不具合を、仕様として許容される振る舞いにしてはなりません。  
既知の事象によって保証できない範囲がある場合は、原因や実装状況ではなく、保証しない条件と利用側が選べる代替機能を記載します。

## 文書の参照方向

機能仕様は、上位の要求、外部標準、同じ階層の機能仕様を参照できます。  
API 文書、実装文書、ソース、テストなど、機能仕様より下流の成果物は参照しません。

下流成果物は、設計判断または検証対象の根拠を示す必要がある場合に、機能仕様の要件 ID と UUID を参照できます。  
参照は、API のまとまり、設計判断、代表的な検証項目など、要件との対応を説明する意味がある単位に限定します。  
すべての関数、ソース行、テストの確認文へ機械的に要件との対応を付与してはなりません。

下流成果物から参照する場合は、要件 ID と UUID を一組で記載します。  
媒体ごとの記法は、「下流成果物での参照記法」に従います。

機能仕様から下流成果物への逆参照は追加しません。

## 要件 ID と UUID

要件 ID は、次の形式とします。

```text
CPLAT-<CATEGORY>-<TYPE>-NNN
```

`<CATEGORY>` は、機能仕様のファイル名に対応する大文字のカテゴリ名です。  
`<TYPE>` は、要件の種別に対応する種別コードです。  
`NNN` はカテゴリと種別の組み合わせごとに `001` から始まる 3 桁以上の連番です。

例を次に示します。

```text
CPLAT-CLOCK-FUNC-001
CPLAT-HASHTABLE-QUAL-001
```

要件 ID は、人が要件のカテゴリ、種別、系列内の識別番号を読み取るために使用します。  
要件のカテゴリや種別の見直しによって、設計または製作中に変更される可能性があります。

各要件には、要件 ID とは別に UUID を一つ付与します。  
UUID は、小文字の 16 進数とハイフンによる UUIDv4 の標準表記とします。

```text
123e4567-e89b-42d3-a456-426614174000
```

UUID は、要件 ID が変わった場合も同じ論理要件を追跡するための永続識別子です。  
同じ論理要件である限り、要件文、種別、カテゴリ、連番を変更しても UUID を変更してはなりません。

要件 ID と UUID の対応の正本は、各機能仕様の「機能要件」に記載します。  
別の対応表は作成しません。

## 要件の種別

要件の種別と種別コードは、次の 4 種類です。

| 種別コード | 種別 | 対象 |
|---|---|---|
| `FUNC` | 機能 | cplat が提供する処理と、外部から観測できる結果 |
| `QUAL` | 品質 | 安全性、信頼性、性能、再現性など、処理の性質に対する保証 |
| `COMP` | 互換性 | プラットフォーム、保存形式、通信形式、ABI などの間で維持する性質 |
| `CONS` | 制約 | 下流設計が守る必要のある方式または選択範囲 |

利用側が守る条件は、cplat 自身が満たす要件ではありません。  
利用側の条件には要件 ID を付けず、「前提と制約」に記載します。

## 要件の記述形式

要件は、次の表へ記載します。

| 要件 ID | cplat の要件 |
|---|---|
| `CPLAT-EXAMPLE-FUNC-001` <!-- cplat-req: uuid=123e4567-e89b-42d3-a456-426614174000 --> | cplat の例示機能は、指定された入力を処理し、結果を利用側へ返します。 |

UUID は、要件 ID の直後に一つの HTML コメントとして記載します。  
HTML コメントは Markdown の表示には現れませんが、要件 ID と UUID の対応を機械的に読み取れます。

一つの行には、一つの要件だけを記載します。  
複数の条件または結果が互いに独立して変更できる場合は、要件を分けます。

要件文では、要件 ID のカテゴリに対応する機能を主語とし、条件、処理、観測できる結果を明確にします。  
要件文を単独で引用した場合も責務の主体を特定できるように、主語は省略しません。  
`cplat は` や `本機能は` など、機能カテゴリを特定できない主語は使用しません。

カテゴリごとの主語は、次の表に従います。

| カテゴリ | 主語 |
|---|---|
| `ARGPARSER` | cplat のコマンド ライン引数解析機能 |
| `BASE` | cplat の基盤機能 |
| `CLOCK` | cplat の時計・時刻機能 |
| `COMPRESS` | cplat の圧縮機能 |
| `CONSOLE` | cplat のコンソール機能 |
| `CRT` | cplat の C ランタイム抽象機能 |
| `CRYPTO` | cplat の暗号機能 |
| `HASHTABLE` | cplat のハッシュ テーブル機能 |
| `MMAP` | cplat のメモリ マップド ファイル機能 |
| `NET` | cplat のネットワーク機能 |
| `PROMPT` | cplat のプロンプト機能 |
| `REGEX` | cplat の正規表現機能 |
| `RUNTIME` | cplat の実行時支援機能 |
| `SYNC` | cplat の同期機能 |
| `TRACE` | cplat のトレース機能 |
| `WIN32` | cplat の Win32 UTF-8 ラッパー機能 |

主語と同じ機能名を後続の文で繰り返さず、対象となる操作または状態を具体的に記載します。  
`対象`、`それ`、`同じ` などの指示語は、要件文の中だけで参照先を特定できる場合に限って使用します。

条件がある場合は、「〜の場合」の形で条件を先に示します。

「適切に」「安全に」「必要に応じて」など、満足したかを判断できない表現は使用しません。  
数量が契約に必要な場合は値を明示します。  
上位条件によって値が決まる場合は、具体値を実装から逆算せず、cplat が保証する範囲を記載します。

背景、理由、例外、利用側への注意は要件文へ詰め込まず、対応する機能別の節で説明します。

## 下流成果物での参照記法

Markdown では、表示する要件 ID の直後に、正本と同じ UUID を HTML コメントで記載します。

```markdown
要件: `CPLAT-CLOCK-FUNC-001` <!-- cplat-req: uuid=123e4567-e89b-42d3-a456-426614174000 -->
```

C または C++ の製品コードでは、通常のブロック コメントへ要件 ID と UUID を記載します。

```c
/* cplat-req: id=CPLAT-CLOCK-FUNC-001; uuid=123e4567-e89b-42d3-a456-426614174000 */
```

公開宣言と対応付ける場合は、生成する API 文書へ要件情報を混入させないため、要件コメントを Doxygen コメントより前に置きます。  
複数の要件と対応する場合は、要件ごとにブロック コメントを分けます。

テストでは、テスト項目の説明に続く `//` コメントへ要件 ID と UUID を記載します。  
説明コメント、要件コメント、テスト マクロの間に空行を入れてはなりません。

```cpp
// 単調増加クロックが時刻補正の影響を受けないことを確認する。
// cplat-req: id=CPLAT-CLOCK-FUNC-001; uuid=123e4567-e89b-42d3-a456-426614174000
TEST(clockTest, monotonic_clock_is_not_adjusted)
{
    // Arrange
```

`TEST`、`TEST_F`、`TEST_P`、`TYPED_TEST` のすべてで同じ配置規則を使用します。  
要件コメントはテスト エビデンスの概要へ出力します。

要件コメントだけをテスト項目の説明にしてはなりません。  
テストの目的を示す説明を先に記載します。

一つのテストが複数の要件と対応する場合は、説明の後ろへ要件コメントを要件ごとに記載します。  
個々の確認やアサーションへ同じ要件情報を重複して記載しません。

## 要件 ID と UUID の変更

新しい要件 ID は、カテゴリと種別の組み合わせにおいて、Git 履歴を含めて過去に使用した最大番号より大きい番号とします。  
廃止した要件 ID は再利用しません。

要件の種別またはカテゴリを変更する場合は、移動先の系列で新しい要件 ID を付与し、UUID を維持します。  
意味を保った表現修正、節の移動、要件の具体化でも UUID を維持します。

一つの要件を複数へ分割する場合、複数の要件を統合する場合、別の論理要件へ置き換える場合は、既存の ID と UUID を廃止します。  
分割または統合後の各要件には、新しい ID と UUID を付与します。

## 各文書の構成

各機能仕様は、次の見出しで構成します。

1. 概要
2. 解決する課題
3. 機能要件
4. 機能別の振る舞い
5. 適用範囲外
6. 前提と制約
7. 選択の指針
8. 関連する機能仕様と外部仕様

「概要」「解決する課題」「機能要件」「適用範囲外」「前提と制約」は必須です。  
内容がない場合も見出しを残し、「該当する項目はありません」と記載します。

「機能別の振る舞い」は、機能のまとまりごとに具体的な見出しへ置き換えます。  
正常な振る舞い、代替結果、失敗時の振る舞い、状態変化、プラットフォーム差、保証範囲から、その機能の理解に必要な内容を記載します。

「選択の指針」と「関連する機能仕様と外部仕様」は、該当する内容がある場合だけ設けます。

## 文書の分割単位

一つの文書は、利用側から見て一つの目的を持つ機能カテゴリを扱います。  
実装ディレクトリまたは公開ヘッダーの分割を、機能仕様の分割根拠にしてはなりません。

一つのカテゴリに複数の操作がある場合でも、同じ課題と前提を共有する場合は一つの文書にまとめます。  
課題、利用条件、変更理由を独立して説明する必要がある場合は、別の機能カテゴリとして分割します。

## 変更時の扱い

機能の追加、削除、外部から観測できる振る舞いの変更は、対応する機能仕様へ先に反映します。  
その後、下流成果物を機能仕様へ適合させます。

機能仕様を変更するときは、同じカテゴリの要件間と、関連する機能仕様との矛盾を確認します。  
要件 ID と UUID の追加、維持、廃止は、本書の「要件 ID と UUID」に従います。

## 確認

機能仕様の変更後は、次の項目を確認します。

- すべての要件 ID と UUID が所定の形式であり、文書群全体で重複していないこと
- 要件 ID のカテゴリと種別が、文書名および要件の内容と一致すること
- 各要件文が、要件 ID のカテゴリに対応する主語で始まること
- Markdown、製品コード、テストの要件参照が媒体ごとの記法に従うこと
- 下流成果物が参照する UUID が正本に存在し、要件 ID がその UUID の現在の ID と一致すること
- 各要件が cplat 自身の責務であり、利用側や上位アプリケーションの責務を含まないこと
- 各要件文が一つの要求だけを持ち、条件と観測可能な結果を判定できること
- API 名、実装方式、ソース、テストへの参照がないこと
- 前提、保証範囲、適用範囲外が要件と矛盾しないこと
- 関連する機能仕様との用語と役割分担が一致すること

Markdown の表記と文章は、[日本語技術文書の文章規範](../../../framework/docsfw/docs/japanese-technical-writing-guideline.md) と [text_style_jp](../../../framework/docsfw/bin/text_style_jp.md) に従って確認します。

要件 ID と UUID の形式および参照関係は、c-platform のルートで次のコマンドを実行して確認します。

```shell
python3 bin/check_functional_spec.py
```
