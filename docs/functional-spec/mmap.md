# メモリ マップド ファイル (mmap) 機能仕様

## 概要

メモリ マップド ファイルは、ファイルの内容をプロセスのアドレス空間へ写し、通常のメモリと同じように読み書きできるようにする機能です。  
対象は `cplat/mmap/mmap.h` が公開する `cplat_mmap_*` の一群です。

本書は、この機能が満たす要件と、その解決策として用意した機能を説明します。  
標準 I/O との使い分けは [ファイル入出力 API の選定基準](../fileio-api-selection-guideline.md) を参照してください。

## 解決する課題

ファイルの一部を繰り返し読み書きする処理を標準 I/O で書くと、位置の移動と読み書きの呼び出しが毎回必要です。  
呼び出しごとにデータの複製も発生します。

メモリ マップド ファイルはこれを避けられますが、API がプラットフォームで大きく異なります。  
Linux は 1 つの関数でマップできる一方、Windows はファイルを開き、マッピング オブジェクトを作り、ビューをマップする 3 段階を踏みます。  
解放も、Linux は 1 つの関数、Windows はビューの解放とハンドルの解放に分かれます。

さらに、同じファイルを複数のプロセスがマップする場合は、排他制御が別途必要です。  
ロックの識別子をマップ対象と一致させる管理も、利用側の負担になります。

本機能は、これらを 1 つのハンドルにまとめ、必要になったときだけ排他制御を用意します。

## 要件と機能の対応

| 要件 | 解決する機能 |
|---|---|
| ファイルをアドレス空間へ写す | ファイルのオープンとマップを一括で行うアタッチ |
| 解放を 1 回の呼び出しで済ませる | ビューとハンドルをまとめて解放するデタッチ |
| 新しいファイルを作ってマップする | 読み書きモードでの新規作成とサイズ指定 |
| 書き込みをディスクへ反映する | 明示的なフラッシュ |
| 複数のプロセスから同じファイルを扱う | マップ対象と同じ識別子のプロセス横断読み書きロック |
| 排他が不要な用途でコストを払わない | ロックの遅延生成 |

## アタッチとデタッチ

アタッチは、パスとアクセス モードを受け取り、ファイルのオープンとマップを 1 回の呼び出しで行います。  
成功すると、マップされたアドレスとサイズを取得できるハンドルが返ります。

アクセス モードは読み取り専用と読み書きの 2 つです。  
読み取り専用は既存のファイルだけを対象とし、存在しない場合は失敗します。  
読み書きは、ファイルが存在しなければ指定したサイズで新規に作成します。

既存のファイルを開いた場合、マップのサイズはその時点のファイル サイズになります。  
新規作成時のサイズ指定は無視します。

デタッチは、マップの解放とハンドルの解放をまとめて行います。  
内包するロックがあれば、それも同時に破棄します。

## 書き込みの反映

マップした領域への書き込みは、いつディスクへ反映されるかを OS が決めます。  
特定の時点までの内容を確実に残したい場合は、明示的なフラッシュを呼びます。

フラッシュが保証するのは、ローカル ファイル システムへの書き込みまでです。

## プロセス横断の排他

同じファイルを複数のプロセスがマップする場合の排他は、プロセス横断の読み書きロックで行います。  
このロックは、マップ対象のパスを識別子として使うため、利用側がロックの名前を決める必要がありません。

ロックは、ハンドルから取得する API を最初に呼んだ時点で用意します。  
排他が不要な用途では生成しないため、そのコストを負担しません。

取得したロックは、同期機能のプロセス横断読み書きロックとして、そのまま操作します。  
ロックの詳細は [同期 (sync) 機能仕様](sync.md) を参照してください。

## 適用範囲外

次の項目は本機能が扱いません。

- 部分範囲のマップ。オフセットと長さを指定したマップはできません。
- 追記によるファイルの伸長。既存ファイルを開くと、その時点のサイズが固定のマップ サイズになります。
- サイズが 0 のファイル。マップの結果が 0 バイトになる場合はアタッチが失敗します。
- 匿名マッピング。対象はファイルに限ります。

## 前提と制約

本機能はローカル ファイル システム上のファイルを対象とする設計です。  
NFS などのネットワーク ファイル システムでは、プロセス間、特にホストをまたいだ一貫性を保証しません。

保証できない理由は 3 つあります。  
アドバイザリ ロックがネットワーク ファイル システム上では信頼できないことがあります。  
フラッシュが反映するのはサーバーへの書き込みまでで、他のクライアントのキャッシュを無効化しません。  
他のクライアントがすでにマップしたページは、ロックの取得と解放だけでは最新化されません。

ネットワーク ファイル システム越しの共有が必要な場合は、本機能ではなく別の方式を検討してください。

## 選択の指針

標準 I/O のラッパーとメモリ マップド ファイルのどちらを使うかは、アクセス パターンとファイル サイズで決まります。  
測定に基づく判断手順は [ファイル入出力 API の選定基準](../fileio-api-selection-guideline.md) を参照してください。

上記の適用範囲外に該当する用途、すなわち追記による伸長、部分範囲のマップ、空ファイルの扱いが必要な場合は、標準 I/O のラッパーを使います。
